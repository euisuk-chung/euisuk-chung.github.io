## 논문 개요와 전체 구조

도구를 쓰는 LLM 에이전트는 검색 결과나 계산값을 받아 답변을 작성합니다. 서버가 오류를 내거나, 예상과 다른 타입을 보내거나, 형식은 정상인데 값이 틀린 결과를 돌려줄 수도 있습니다. 에이전트가 답변을 작성하고 종료했더라도 작업에 필요한 근거를 얻었는지는 따로 확인해야 합니다. 저자들은 에이전트와 서버 사이에서 MCP(Model Context Protocol) 도구 호출을 가로채는 **MCP-Injector**를 만들어 이 차이를 실험했습니다. [논문 §1][s1]

공개 MCP 저장소 1,774곳에서 수집하고 필터링한 스레드 57,240개로 장애 유형과 지속성의 스트레스 프로필을 구성했습니다. 이 조건의 작업 완료 점수는 10점 만점에 평균 8.08에서 3.23으로 내려갔습니다. gpt-oss-20B와 120B를 비교한 결과, 장애가 없을 때의 점수를 얼마나 유지했는지 나타내는 비율에서 120B의 우위는 검출되지 않았습니다. 이 결과는 두 모델, 세 실행 스택, 단일 서버 과제 25개, 영구 장애 비중이 큰 프로필에 관한 것입니다. [논문 §§4–6][s4]

## 핵심 기여와 혁신성

1. **도구가 실패하는 위치를 실험 변수로 만들었습니다.** MCP 호출 경계에서는 잘못된 결과도 정상 JSON처럼 전달될 수 있습니다. 프록시는 에이전트가 실제로 받는 응답 값·오류·지연을 조작하면서 기존 클라이언트와 도구 구현을 그대로 연결합니다. [논문 §3][s3]
2. **실패 유형과 지속성을 함께 정합니다.** 같은 오류라도 이후 호출마다 돌아오는지, 한 호출에 그치는지에 따라 재시도의 결과가 달라집니다. 공개 장애 보고에서 얻은 18개 규칙을 사용하고, 규칙의 선택 가중치와 실제 실행 중 발동 비중을 각각 확인합니다. [논문 §4][s4] · [부록 C][a3]
3. **실행 종료, 답변 품질, 도구 근거를 별도로 측정합니다.** 대부분 실행이 종료하는 상황에도 품질이 크게 떨어졌고, 도구를 호출하지 않은 그럴듯한 답변에 점수가 붙기도 했습니다. 이를 통해 정상 조건에서의 능력과 장애 조건에서 유지되는 품질을 따로 비교할 수 있습니다. [논문 §§5–6][s6]

## 기술적 세부사항

MCP는 클라이언트가 이름과 인자를 지정해 서버 도구를 호출하고 결과나 오류를 받는 규약입니다. 프록시는 에이전트 쪽에서 MCP 서버로, 실제 도구 쪽에서 MCP 클라이언트로 동작합니다. 도구 이름·인자·문맥을 관찰하고, 프로필·지속 상태·시드 기반 난수에서 연산자를 결정합니다. 요청을 보내기 전에 오류를 합성하거나, 실제 서버 응답을 받아 내용을 바꿀 수 있습니다. 발동한 주입 사건은 구조화 로그에 남습니다. [논문 §3.1과 그림 1][f1]

![에이전트와 MCP 서버 사이에서 프록시가 요청을 관찰하고 규칙을 정해 요청이나 응답에 적용한 뒤 주입을 기록하는 구조]({{ '/img/reviews/2026/mcp-injector-agent-fault-tolerance-review/mcp-call-boundary.svg' | relative_url }})

요청과 결과가 프록시를 지나는 위치입니다. [리뷰어 작성, 논문 그림 1 및 §3.1, PDF 3쪽 기반][pdf3]
{: .caption}

**Proxy-off**는 프록시 자체를 제거한 기준선, **OP0**는 내용을 바꾸지 않는 프록시, **OPP**는 18개 규칙의 장애 프로필이 활성화된 프록시입니다. Proxy-off와 OP0를 비교해 프록시 자체의 영향을 확인하고, OP0와 OPP를 비교해 같은 프록시에서 장애를 켰을 때 달라진 결과를 측정합니다. 스택·모델·과제·시드를 맞춘 각 쌍의 OPP 점수에서 OP0 점수를 빼면 품질 변화량을 얻습니다. [논문 §5.2][s52] · [부록 B][a2]

**완료율**은 시간 제한, 반복 상한, 미처리 예외 때문에 중단되지 않고 실행이 끝난 비율입니다. **작업 완료 점수**는 도구 선택과 계획, 과제 이행을 포함하는 0~10점 품질 척도입니다. 논문은 주 분석에서 OPP 미완료를 0점으로 반영하고 양쪽 조건에서 완료된 셀도 따로 비교합니다. 완료 실행의 답변마다 LLM 심사 모델을 다섯 번 실행하고 중앙값을 취했습니다. [논문 §5.3–5.4][s53] · [부록 D][a4]

## 챕터별 상세 리뷰

### 📖 **Chapter 1: Introduction**

도구의 스키마와 서비스 상태, 통신 방식은 에이전트 품질에 관여합니다. 정상 도구를 전제로 평가하면 형식은 맞지만 틀린 값을 그대로 사용하거나, 같은 오류에 반복 호출을 보내는 에이전트의 행동을 측정하기 어렵습니다. 저자들은 네트워크 계층보다 MCP 도구 호출 경계에 가까운 실험을 구성합니다. 공개 장애 보고로 만든 프로필, 이를 적용하는 미들웨어, 같은 과제를 조건별로 반복하는 실험이 연구의 세 부분입니다. [논문 §1][s1]

### 📖 **Chapter 2: Background and Definitions**

호출의 요청과 결과 또는 오류가 관찰 경계입니다. 예상과 달라진 서비스 상태가 **failure**이고, 이를 일으킨 버그·설정 오류·의존 서비스의 중단이 **fault**입니다. 서버의 내부 원인을 재현하지 않고도 에이전트가 관찰하는 현상을 인터페이스에서 만들어 후속 판단을 조사할 수 있습니다. MCP의 프롬프트·리소스·스트리밍과 보안 공격은 실험 범위 밖입니다. [논문 §2][s2]

내용 실패는 도착한 값이나 형식이 잘못된 경우이고, 시간 실패는 결과가 지나치게 늦거나 도착하지 않는 경우입니다. 시간에 따른 지속성은 한 번 발동하고 해소되는 일시적(transient), 정상과 실패가 섞여 나타나는 간헐적(intermittent), 활성화 이후 매번 나타나는 영구적(permanent)으로 나눕니다. 다음 절은 이 구분을 호출별 스케줄로 옮깁니다. [논문 §2][s2]

### 📖 **Chapter 3: MCP-Injector**

#### 3.1 Architecture

프록시는 MCP 클라이언트 라이브러리의 호출 훅을 가로챕니다. 요청 단계에서는 지연·무응답·합성 오류를 만들 수 있고, 결과 단계에서는 실제 응답의 내용이나 타입을 바꿉니다. 이 구성을 사용하면 실제 서버 권한을 변경하지 않고도 에이전트가 권한 오류를 받고 다른 도구를 택하는지 볼 수 있습니다. [논문 §3.1][s31]

#### 3.2 Fault API

설정은 무엇을 바꿀지 정하는 **연산자**, 얼마나 지속할지 정하는 **스케줄**, 어느 도구 호출에 적용할지 정하는 **범위**를 분리합니다. 다음 표는 원문 연산자의 동작입니다. [논문 표 1][t1]

| 연산자 | 호출 경계에서 관찰되는 동작 |
| --- | --- |
| OP0 | 요청과 결과를 그대로 통과 |
| OP1 | 문자의 일부를 바꾸는 작은 내용 오류 |
| OP2 | 단어 수준의 치환으로 의미상 잘못된 결과 생성 |
| OP3 | 예상 스키마에 맞지 않는 타입으로 강제 변환 |
| OP4 | 구조화된 MCP 오류 반환 |
| OP5 | 반환 전 인위적 지연 |
| OP6 | 호출을 대기 상태에 두어 응답을 보내지 않음 |

영구 규칙은 한 번 활성화되면 범위가 맞는 호출마다 발동합니다. 일시 규칙은 한 호출에 적용하고 초기화하며 이 실험에서는 선택된 호출에 확실히 적용됩니다. 간헐 규칙은 상태를 유지하는 동안 호출마다 설정 확률로 발동하고, 해제 확률에 따라 새 규칙을 뽑습니다. 시드와 호출 이력이 같으면 주입 결정은 재현됩니다. 모델이 고른 호출 이력이나 평가 모델의 점수는 달라질 수 있습니다. [논문 §3.2][s32] · [부록 A][a1]

### 📖 **Chapter 4: Fault Profile Methodology**

저자들은 2025년 9월 MCP Market과 Awesome MCP Servers에서 공개 저장소 1,774곳을 선정했습니다. 이슈·PR과 연결된 활동을 시간순으로 묶어 103,166개 스레드를 얻었습니다. 키워드로 분할하고 교차 링크 중복, 빌드 관련 항목, 비영어 자료를 제거하자 57,240개가 남았습니다. gpt-4o-2024-08-06을 temperature 0과 고정 JSON 스키마로 사용해 장애 유형과 지속성을 분류했습니다. 층화 추출한 117개를 두 연구자가 독립 표기하고 세 번째 연구자가 불일치를 조정했습니다. 코언 카파는 유형 0.93, 지속성 0.80입니다. [논문 §4와 그림 2][s4]

57,240개 가운데 비장애 분류는 42,411개였습니다. 유형과 지속성이 모두 정해진 13,824개가 다음 표와 가중치의 분모를 이룹니다. 불확실하다고 분류된 유형이나 지속성은 제외했습니다. [논문 표 2][t2] · [부록 A 표 3][t3]

| 실패 유형 | 간헐 | 영구 | 일시 |
| --- | ---: | ---: | ---: |
| 응답 지연 | 51 | 157 | 1 |
| 명시적 오류 | 669 | 9,075 | 97 |
| 잘못된 값 | 155 | 1,733 | 1 |
| 잘못된 형식·타입 | 47 | 511 | 1 |
| 작은 내용 오류 | 15 | 177 | 0 |
| 무응답 | 167 | 963 | 4 |
| 합계 | 1,104 | 12,616 | 104 |

영구 장애는 가중치의 91.3%이며, 영구적 명시 오류 항목 하나가 약 65.6%입니다. 이 수치는 이슈에서 관찰한 **실패 양상의 상대 빈도**입니다. 전체 정상 호출 수를 관찰하지 않았고 공개 이슈에서 재현하기 쉬운 장애가 과대표집될 수 있으므로, 저자들은 스트레스 프로필로 해석합니다. 주입 시 30초 지연, 간헐 규칙 해제 확률, 내용 변형 강도는 고정 설정값입니다. [논문 §4][s4] · [부록 A][a1]

### 📖 **Chapter 5: Experimental Protocol**

#### 5.1 Benchmark and Task Set

MCP-Bench의 과제 생성 절차을 사용했습니다. 연결을 시도한 서버 28개 중 연결된 25개에서 과제 25개를 만들었습니다. 에이전트에는 일상 언어로 작성한 요청을 주고, 세부 요구사항은 채점 참조에만 사용합니다. 무관한 서버는 넣지 않았습니다. 한 서버가 여러 도구를 제공하므로 단일 서버 과제도 여러 호출을 요구할 수 있습니다. [논문 §5.1][s51]

#### 5.2 Experimental Factors

백본은 gpt-oss-20B와 120B입니다. 배포된 MXFP4 정밀도, 16,000토큰의 문맥창, 기본 디코딩 설정을 사용했습니다. 세 스택은 MCPBench의 여러 라운드에 걸친 계획·실행, OpenAI Agents SDK, LangChain/LangGraph입니다. 입력 프롬프트, 도구 스키마, 문맥 예산과 시간 제한은 공통으로 두었습니다. 백본 2종 × 스택 3종 × 조건 3종 × 과제 25개 × 시드 3개로 총 1,350개 셀을 구성했습니다. OPP에 450개, OPP의 각 모델에 225개, 모델·스택 조합에 75개가 배정됩니다. [논문 §5.2][s52] · [부록 D 표 4][t4]

#### 5.3 Execution and Run Policy

#### 6.3 Scale Does Not Purchase Fault Tolerance

같은 스택·모델·과제·시드 셀의 작업 완료 점수로 유지율을 계산합니다. 아래 식은 원문의 비율을 기호로 나타낸 것입니다. [논문 §6.3][s63]

```math
R = \frac{S_{\mathrm{OPP}}}{S_{\mathrm{OP0}}}
```

분자는 장애 주입 상태의 점수, 분모는 같은 프록시가 장애를 주입하지 않을 때의 점수입니다. 1은 점수 유지, 1보다 작은 값은 점수 하락을 뜻합니다. 미완료를 0점으로 처리한 유지율 모형에서 모델 크기 계수는 −0.009, 95% 신뢰구간은 [−0.39, 0.37], p=0.96이었습니다. 신뢰구간에는 개선과 악화가 모두 포함됩니다. [논문 §6.3][s63]

OP0 대비 OPP의 짝지은 완료율 하락은 120B −5.8%포인트, 20B −3.6%포인트이고, 두 하락 폭 차이의 95% 신뢰구간은 [−3.0, 7.5]입니다. OPP에서 완료한 실행의 점수는 120B 3.68, 20B 3.26으로 완료율과 다른 순서를 보였습니다. [논문 §6.3][s63] · [부록 D 표 4][t4]

120B는 OPP 셀당 평균 주입 4.6회(20B 3.9회), OP0 출력 평균 2,063토큰(20B 1,711토큰)을 기록했습니다. 저자들은 장애 노출, 공동 16K 문맥창 안의 긴 출력, 스택의 호출량 차이를 가능한 설명으로 검토합니다. 실험에서는 이런 요인들을 따로 개입해 인과 효과를 식별하지 않았습니다. [논문 §6.3][s63] · [§7][s7]

### 📖 **Chapter A: Fault Profile Calibration Details**

여섯 연산자와 세 지속성 조합마다 하나의 규칙이 있습니다. 식 (1)에서 분자 $`n_{m,p}`$는 실패 유형 $`m`$과 지속성 $`p`$가 모두 확인된 스레드 수입니다. 분모 $`N`$은 해당 조건을 만족해 주입할 수 있는 13,824개입니다. 영구적 명시 오류는 9,075개이므로 9,075를 13,824로 나눈 약 0.6565의 가중치를 갖습니다. 이 가중치는 새 규칙을 뽑을 때 적용됩니다. [부록 A 식 (1)·표 3][a1]

```math
w_{m,p} = \frac{n_{m,p}}{N}
```

간헐 장애의 활성 확률 $`a`$를 정할 때 저자들은 두 상태를 오가는 이상적인 스케줄의 정상상태 장애 비율을 사용했습니다. 식 (2)의 $`\mathrm{INT}`$와 $`\mathrm{PERM}`$은 같은 장애 유형의 간헐·영구 보고 수입니다. 해제 확률 $`d`$는 0.3으로 고정했습니다. 첫 식을 $`a`$에 대해 풀면 두 번째 식을 얻습니다. 지연의 경우 $`0.3 \times 51/157`$로 약 0.0975입니다. [부록 A 식 (2)][a1]

```math
\frac{a}{a+d} = \frac{\mathrm{INT}}{\mathrm{INT}+\mathrm{PERM}}
```

```math
a = d \cdot \frac{\mathrm{INT}}{\mathrm{PERM}}
```

실제 구현은 간헐 규칙을 **보유하는 동안 각 호출에 독립적으로 확률 $`a`$**를 적용하며, 이후 호출마다 확률 $`d`$로 해제합니다. 평균 보유 길이는 $`1 + 1/d`$, 약 4.3호출입니다. 따라서 위 분수로 설정값을 정했더라도 발동 빈도는 상태 보유 중의 독립 시행과 호출 이력에 좌우됩니다. 일시적 규칙은 한 번 발동하고, 영구적 규칙은 매번 발동합니다. OP5는 HTTP 전송 제한 60초보다 짧은 30초 지연을, OP1·OP2는 단어별 변형 확률 0.08과 0.35를 사용합니다. OP1 변형 강도는 0.05이며 OP3·OP4·OP6에는 추가 조정값이 없습니다. [부록 A][a1]

### 📖 **Chapter B: Proxy Non-Intrusiveness: Full Analysis**

동일한 스택·모델에서 과제·시드를 짝지어 Proxy-off와 OP0를 비교했습니다. 조합 6개와 종합 점수 3개의 윌콕슨 부호순위 검정 18개에서 본페로니 보정 후 논문이 유의하다고 보고한 결과는 없습니다. 가장 작은 보정 p값은 반올림 0.050이고, 평균 점수 차이의 최대 절댓값은 0.55점입니다. 호출당 프록시 오버헤드는 약 0.1~0.5초로 추정했습니다. 이 검사는 현 실험에서 계측 영향이 체계적으로 나타나는지 확인하며, 사전에 정한 동등성 마진에 대한 검정까지 보고한 것은 아닙니다. [부록 B와 그림 5][a2]

### 📖 **Chapter F: Agent Stack Orchestration Details**

MCPBench는 각 라운드에 계속 여부와 도구 호출 목록을 JSON으로 정하고 목록의 호출을 병렬 실행합니다. 오류는 누적 정보 버퍼로 돌아가 다음 계획 입력이 됩니다. OpenAI Agents SDK는 한 메시지 루프에서 도구 결과 메시지를 붙이고, MCP 오류를 구조화된 오류 결과로 전달합니다. LangChain은 LangGraph의 모델·도구 노드를 번갈아 실행하고 미들웨어에서 예외를 도구 메시지로 반환합니다. 두 메시지 기반 스택에서는 모델이 추가 호출 없는 텍스트를 내면 루프가 종료됩니다. 세 스택 모두 다음 도구를 재시도하거나 바꾸는 결정은 모델이 내립니다. [부록 F 표 6][t6]

### 📖 **Chapter G: Behavioral Adaptation: Reasoning Traces and Retry Loops**

저자들은 장애 직후 다음 도구 호출이 같으면 재시도, 다르면 전환, 추가 호출 없이 완료하면 대체 응답, 추가 호출 없이 미완료면 타임아웃으로 분류했습니다. 이 기준으로 분류한 **장애 인접 호출 1,302건**에서 MCPBench는 전환 68%, LangChain은 대체 응답 44%, OpenAI SDK는 대체 응답 49%였습니다. 이 분류의 집계 단위는 호출입니다. §6의 시스템 미완료는 전체 셀을 셉니다. 이 절의 장애 인접 호출 분류에는 타임아웃이 관찰되지 않았습니다. [부록 G와 그림 8][a7]

동일한 실패 도구에 연속 세 번 이상 요청한 실행은 38개였고, MCPBench 25개, LangChain 7개, OpenAI SDK 6개였습니다. 저자들이 확인한 MCPBench·120B 계획 기록에서 모델은 인자나 형식을 추정했지만 영구 장애인지 일시 장애인지 구별하지 않았습니다. 한 과학 계산 과제는 22회 호출 중 12회 연속 재시도를 남겼습니다. [부록 G][a7]

### 📖 **Chapter H: Task-Domain Sensitivity**

과제별로 의존성 분석에 등장하는 서로 다른 도구 호출을 세어 깊이 6~29를 얻고, 여섯 도메인으로도 분류했습니다. 과제별 점수 유지율 중앙값과 깊이의 스피어만 상관은 0.29(p=0.17, 과제 25개)입니다. 깊이와 평균 주입량의 상관은 0.47(p=0.02)이었고, 주입량을 고려한 부분 상관은 0.35(p=0.09)였습니다. 깊이가 저하를 유발했다는 결론을 논문은 내리지 않습니다. [부록 H와 그림 9][a8]

업무 유형별 중앙값은 상태를 다루는 금융 과제 0.04(2개), 개발 도구 0.05(4개), 실시간 API 0.06(4개), 상태 없는 검색 0.18(8개), 순수 계산 0.60(2개), 여러 단계의 순차 작업 0.61(5개)입니다. 크루스칼–왈리스 검정 p=0.08이므로 유형별 차이는 기술 통계로 읽는 것이 적절합니다. [부록 H][a8]

## 실험 결과 심층 분석

**완료율과 품질에 분모를 붙이면 결과가 달라 보입니다.** 전체 OPP 셀 450개 중 420개가 완료했습니다. 주 분석의 평균은 OPP 미완료에 0점을 부여하고, 두 조건 모두 완료한 셀만 고른 분석은 완료 가능한 과제로 범위를 좁힙니다. 평균 하락률이 각각 60%, 57%라는 점은 저하가 종료 실패에만 집중되지 않았음을 보여 줍니다. 원문의 아홉 품질 지표는 짝지은 윌콕슨 검정에서 Benjamini–Hochberg 보정 후 모두 p<0.001이었습니다. [논문 §6.1][s61] · [부록 D 표 4·5][a4]

**스택 간 차이와 모델 크기 비교는 별개의 추정입니다.** 스택 분석의 추가 하락 −0.93점과 −0.84점은 LangChain과의 조건 상호작용으로, 주입량을 맞춘 실험값이 아닙니다. 백본 분석에서는 각 모델의 평소 점수 대비 유지율과 완료율 하락 폭을 따로 살폈습니다. OPP 완료율 차이 4.4%포인트에는 정상 조건에서 이미 존재한 완료율 격차가 포함됩니다. 120B의 완료 응답에 더 높은 점수가 나타난 것은 살아남은 실행 집합의 품질에 관한 결과입니다. [논문 §6.2–6.3][s62]

## 기술적 함의와 응용

도구가 실패할 때에도 에이전트는 텍스트를 반환할 수 있습니다. 시스템의 종료 상태, 사용할 수 있었던 도구 근거, 사용자에게 전달한 답변 품질을 각각 기록하면, 권한이 없는 도구에 계속 요청한 경우와 조회 실패를 설명하고 답변을 마친 경우가 같은 숫자로 합쳐지는 문제를 줄일 수 있습니다. 이 구분은 논문의 완료율·품질·근거 점수에서 얻는 설계상의 해석입니다. [논문 §5.4–6.1][s54]

저자들의 평가 설계는 정상 동작, 프록시 통과, 장애 프로필을 분리하고 각 실행에 선택한 조건과 발동 사건을 연결합니다. 모델과 오케스트레이션을 함께 비교하는 운영 시험에서 어떤 설정이 같았고 어디에서 호출이 달라졌는지 재구성할 수 있습니다. 논문은 이 방식을 다중 서버·장시간 과제와 장애를 고려하는 계획에 확장할 방향을 제시합니다. [부록 C][a3] · [논문 §10][s10]

**검토 범위.** 모델·채점기·프록시를 재실행하지 않았습니다. 원문 도표 전체와 로그 전문은 옮기지 않았고, 비교에 필요한 표와 대표 사례를 추려 원문 수치와 대조했습니다.
