## 논문 개요와 전체 구조

예약을 취소하는 에이전트가 그럴듯한 도구 호출을 만들었다고 해서, 그 예약을 지금 취소해도 되는 것은 아닙니다. 사용자가 취소를 요청했는지, 취소 조건을 만족하는지, 세부 내용을 설명하고 확인을 받았는지는 별개의 문제입니다. **JevAct는 에이전트가 제안한 행동과 실제 실행 사이에서 이 조건들을 검사하는 하네스**입니다. 하네스란 모델 주변에서 도구 호출과 실행 순서를 관리하는 장치를 뜻합니다.

IBM SIL의 *Think Before You Act: Decision Gate for LLM Agents*는 기록에서 계산할 수 있는 사실과 대화를 읽어야 판단할 수 있는 사실을 나눕니다. 날짜·금액·개수는 코드가 확인하고, 사용자 의도·동의·문제 해결 절차는 별도 결정 모델 Kev가 고정된 질문에 확률로 답합니다. 문제가 발견되면 실행 전에 제안을 돌려보내고, 에이전트에게 정해진 횟수만 수정할 기회를 줍니다. 분석 대상은 2026년 10월 28일 제출된 [arXiv v1](https://arxiv.org/abs/2610.38620v1)입니다.

이 연구는 모델의 지능을 높이는 학습법보다 **실행 경계에서 무엇을 검사하고, 그 검사가 실제 과제 성공에 얼마나 도움이 되는지**를 다룹니다. 세 벤치마크 설정에서 총 11종의 에이전트 모델을 평가하지만, 모든 모델을 모든 설정에 사용하지는 않습니다. Telecom의 개선은 일관되게 관찰되며 Airline과 BFCL의 결과는 지표에 따라 섞입니다. 검사 코드·판정 모델·추가 수정 기회가 합쳐진 전체 하네스의 결과라는 점도 함께 읽어야 합니다.

## 핵심 기여와 혁신성

첫 번째 기여는 검증의 위치입니다. 실행이 끝난 뒤 답변을 평가하는 대신, 데이터 변경이나 업무 포기가 실제로 반영되기 직전에 제안을 검사합니다. 다만 다음 행동을 고르는 주체는 여전히 에이전트 LLM입니다. Kev는 독립된 심사자이며, 실행 계획 전체를 대신 만드는 모델이 아닙니다. [1절·2절](https://arxiv.org/html/2610.38620v1#S1)

두 번째는 증거에 맞춘 역할 분담입니다. 무료 수하물 수를 계산할 때는 회원 등급·객실·승객 수를 코드로 계산하고, “사용자가 이 변경을 원했는가”는 대화를 읽는 질문으로 남깁니다. 정책 문서를 질문 목록뿐 아니라 질문 간 관계를 표현하는 불리언 규칙, 기록 기반 검사 함수, 업무 포기 전 체크리스트로 바꾼다는 점이 중요합니다. 서로 다른 취소 자격을 모두 만족해야 한다고 오해하지 않도록 `and`와 `or`를 구분하는 단계도 있습니다. [3절](https://arxiv.org/html/2610.38620v1#S3)

세 번째는 판단 정확도와 에이전트 성공률을 구분해서 평가한 점입니다. 작은 Kev가 더 높은 과제 성공률을 낼 때도, 동일한 상태에 대한 오프라인 판정이 더 정확해서 그런 것은 아니었습니다. 이 결과가 주는 학습 가치는 “좋은 심사 모델을 붙이면 해결된다”는 단순한 설명을 넘어, 입력 길이·확률 임계값·수정 피드백에 대한 에이전트 반응을 함께 보게 한다는 데 있습니다. 이는 리뷰어의 해석이며, 논문도 전체 하네스의 이득을 판정 모델 단독의 기여로 분리하지 않습니다. [5.1절·A.2~A.4](https://arxiv.org/html/2610.38620v1#S5.SS1)

## 기술적 세부사항

JevAct의 입력은 정책 문서, 도구 스키마, 이전 대화와 도구 결과, 현재 제안입니다. 오프라인 컴파일러가 정책별 검사 산출물을 준비한 뒤, 온라인 루프가 선택된 제안만 검사합니다. 출력은 통과 또는 문제 표시와 구체적인 피드백입니다. 통과한 제안은 실행·기록하고, 문제로 표시된 제안은 실행도 기록도 하지 않습니다.

![정책을 질문·코드로 준비하고 에이전트 제안 중 쓰기와 업무 포기만 검사하는 JevAct 흐름]({{ '/img/reviews/2026/jevact-decision-gate-review/verification-flow.svg' | relative_url }})

JevAct의 실행 전 검사 흐름을 한국어로 다시 그렸습니다. 수정 예산이 소진되면 다음 제안은 검사 없이 실행됩니다. 리뷰어 작성, [원문 3절·Figure 2](https://arxiv.org/html/2610.38620v1#S3.F2) 기반.
{: .caption}

다음은 원문 3.2절의 제어 흐름을 옮긴 **설명용 의사코드**입니다. 실제 구현 코드를 실행한 예시는 아닙니다.

```text
입력: 대화 이력 history, 에이전트, 준비한 검사, 검사별 수정 예산 R
proposal ← 에이전트(history)
반복:
    check ← proposal에 적용할 검사 선택
    check가 없거나 해당 수정 예산이 소진되었으면:
        proposal을 실행하고 history에 기록; 종료
    verdict, feedback ← check(proposal, history)
    verdict가 통과이면:
        proposal을 실행하고 history에 기록; 종료
    proposal을 버림; 해당 수정 예산을 1회 사용
    proposal ← 에이전트(history, 이번 호출에만 쓰는 feedback)
```

쓰기 게이트의 수정 예산은 2회, 업무 포기·인계 검사는 1회입니다. **정책 위반을 영구적으로 차단하는 장치로 읽으면 안 됩니다.** 예산을 다 쓰면 다음 제안은 재검사 없이 실행됩니다. 논문이 택한 목적은 무한 차단을 피하면서 제한된 추가 호출로 행동을 고치게 하는 것입니다. 이 동작은 원문의 명시적 설계입니다. [3.2절](https://arxiv.org/html/2610.38620v1#S3.SS2)

결정 모델은 자유로운 설명을 생성하지 않고 선택지별 확률을 한 번의 순방향 계산으로 돌려줍니다. 같은 입력에 대한 여러 질문이 그 계산을 공유합니다. 여기서 “질문 수에 따라 비용이 늘지 않는다”는 설명은 이 공유 방식에 관한 것이며, 모든 입력 길이·서빙 환경에서 지연이 동일하다는 측정 결과는 아닙니다. 어떤 질문을 만들고 어떤 임계값을 적용하는지는 아래 챕터에서 나눠 살펴보겠습니다.

## 챕터별 상세 리뷰

### 📖 **Chapter 1: Introduction**

첫 장은 도구 사용의 결과가 외부 세계에 남는다는 사실에서 출발합니다. 답변의 오류와 예약 취소·기록 수정·상담 종료의 오류는 복구 방식이 다릅니다. 일반적인 에이전트 루프는 모델이 도구 호출을 만들면 곧바로 실행하므로, “생성한 행동”과 “지금 해도 되는 행동” 사이를 별도로 검사할 자리가 비어 있습니다.

저자들은 먼저 ReAct처럼 추론과 행동을 번갈아 수행하는 방식, 그리고 Self-Refine·Reflexion처럼 피드백으로 다음 제안을 개선하는 방식을 소개합니다. 이런 피드백은 도움이 되지만 특정 도구 호출을 실제 반영하기 직전에 정책에 대조하는 것과는 구별됩니다. 별도의 생성형 LLM에게 심사하게 할 수도 있지만, 자유 형식의 설명을 다시 판정으로 해석해야 하고 비용도 추가됩니다.

그 대안으로 고정 선택지와 확률을 반환하는 결정 모델을 둡니다. 다만 확률이 실제 오류 가능성과 잘 맞거나 판단이 정확하다고 가정하지 않습니다. 논문이 던지는 질문은 **이런 모델이 코드 검사와 함께 실행 전 검증을 맡았을 때 전체 에이전트 루프에서 도움이 되는가**입니다. 제안은 에이전트가 만들고 Kev는 검증한다는 경계를 둔 뒤, 다음 장에서 기존 런타임 제어와의 관계를 정리합니다. [1절](https://arxiv.org/html/2610.38620v1#S1)

### 📖 **Chapter 2: Related Work**

**2.1 LLM Agents and Test-Time Feedback.** ReAct는 추론과 환경 행동을 엮고, Self-Refine·Reflexion은 가중치를 바꾸지 않고 실행 중 피드백으로 제안을 고칩니다. JevAct가 이어받는 것은 “다시 제안할 기회”이며, 추가하는 것은 되돌리기 어려운 행동을 실행 전에 정책 조건에 대조하는 단계입니다.

**2.2 Runtime Policy Enforcement.** GuardAgent의 검증 코드 생성, 회사 정책의 실행 가능한 가드 변환, AgentSpec의 트리거·조건·강제 조치, ShieldAgent·CUGA의 정책·거버넌스 개입 등을 순서대로 짚습니다. 이어 ToolSafe·PolicyGuard·PolicyGuide의 모델 기반 검증, 절차 검사 기반 중재, ToolFence의 권한과 심사 결합, CaMeL의 신뢰 제어 흐름과 비신뢰 데이터 분리를 설명합니다. 이 문헌들이 모두 같은 보안 보장을 제공한다는 뜻은 아닙니다. 원문은 접근 방식의 위치를 비교합니다.

JevLoop가 결정 모델에 행동·제어 선택을 맡기는 것과 달리, JevAct는 ReAct LLM의 제안권을 유지합니다. 고정 질문에 대한 확률 임계값, 기록 기반 코드 검사, 피드백을 통한 수정이라는 조합에 초점을 둡니다.

**2.3 LLM Judges and Decision Models.** 완성된 응답을 평가하는 LLM-as-a-judge와 typed choice·점수·확률을 돌려주는 Jev 계열을 연결합니다. 관련 선행 연구는 선호·사실성 판단에서의 경쟁력과 계산·도출이 필요한 질문의 약점, LLM 심사와 겹치는 오류를 보고했습니다. JevAct는 이 모델 유형을 완성된 산출물의 사후 평가가 아니라 행동 실행 전의 온라인 검사에 사용합니다. 이 비교는 논문이 인용한 연구의 역할을 정리한 것이며, 해당 참고문헌 전체를 독립 재평가한 결과는 아닙니다. [2절](https://arxiv.org/html/2610.38620v1#S2)

### 📖 **Chapter 3: Method**

**3.1 Overview.** 에이전트는 이력을 읽고 사용자에게 보낼 텍스트, 도구 호출 또는 둘을 함께 제안합니다. 쓰기 호출은 예약·취소·설정 변경처럼 환경을 바꾸는 행동입니다. hand-off는 사람에게 넘기는 도구 호출뿐 아니라 “더 할 수 있는 일이 없다”며 에이전트의 해결 시도를 끝내는 발언도 포함합니다. 정책이 없는 환경에는 일반적인 함수 호출 검사를 적용할 수 있습니다.

전체 구성은 결정 루프, 컴파일러, 판정 모델, 개별 검사 네 부분입니다. 컴파일러는 도메인별 준비 작업이고, 나머지 부분은 에이전트 실행 중 연결됩니다. 다음 원도식의 위쪽은 정책에서 검사를 만드는 오프라인 경로, 아래쪽은 제안부터 실행 또는 수정까지의 온라인 경로입니다.

**3.2 Decision loop.** 먼저 이력을 조건으로 에이전트가 메시지를 제안합니다. 쓰기 또는 hand-off이면 해당 검사를, 그 외에는 일반 ReAct 실행을 적용합니다. 검사 결과가 문제이면 피드백을 붙여 다시 제안받습니다. 원문의 생성 관계를 옮기면 다음과 같습니다.

```math
m\sim\pi(\cdot\mid h_t),\qquad
m'\sim\pi(\cdot\mid h_t,f).
```

$`h_t`$는 현재까지 확정된 대화 이력, $`\pi`$는 에이전트 모델, $`m`$은 첫 제안, $`f`$는 이번 수정에만 쓰는 피드백, $`m'`$는 수정 제안입니다. 문제로 표시된 제안과 그 피드백은 영구 이력에 남기지 않으므로 과거 비판이 문맥에 계속 쌓이지 않습니다. R회 예산을 쓰고 난 다음 제안을 재검사하지 않는 종료 방식까지 포함해야 이 루프를 정확히 이해할 수 있습니다.

**3.3 Compiler.** 정책과 도구 스키마에서 도구별 예/아니오 질문, 질문들을 조합한 허용 규칙, 이전 도구 결과에서 사실·위반을 계산하는 Python 함수를 만듭니다. 코드 생성과 한 차례 수정에는 개발 로그의 예시 출력도 사용합니다. 손님이 취소를 원했는지와 같은 대화 해석을 코드가 대신 결정하지 않고, 기록이 확정하는 위반만 반환하게 합니다.

업무 인계 체크리스트에는 문제 유형과 해결 단계, 각 단계가 이미 정리되었는지를 묻는 질문이 들어갑니다. 정리되었다는 것은 시도했거나, 정상임을 확인했거나, 적용 대상이 아님을 대화에서 확인했다는 뜻입니다. “해외여행 중이라는 말이 없었다”는 이유만으로 로밍 확인을 끝내면 안 됩니다. **논의하지 않은 조건은 배제된 조건이 아니라는 지시**가 질문 생성에 직접 반영됩니다.

쓰기 질문은 개발 호출의 10%를 초과해 확신 있는 위반을 표시하면 제거합니다. 빈번하게 걸리는 질문은 확보된 증거로 판단하기 어렵거나 정책에 없는 요구일 수 있다는 설계 판단입니다. 인계 단계에는 별도의 필터가 있고, 해결된 학습 에피소드의 인계에서 5%를 초과해 문제로 표시된 단계를 제거합니다. 후자는 해결 여부 라벨을 사용하므로, 모든 준비 과정이 무라벨이라는 설명은 정확하지 않습니다. 실제 단계와 데이터 분리는 A.1에서 이어집니다.

**3.4 Judge.** Kev-27B는 Qwen3.8-27B를 조정한 공개 Jev 유사 결정 모델이며, 이 실험을 위해 추가 학습하지 않습니다. 정책과 대화의 같은 입력을 읽고 여러 고정 질문의 선택지별 확률을 한 번에 출력합니다. 코드가 기록의 수량·날짜를 계산하고 Kev는 의도·동의·절차 수행을 읽도록 역할을 나눕니다. 에이전트 자신이 자기 제안을 채점하지 않지만, 독립 모델을 사용한다는 사실만으로 판단 정확도나 확률 보정이 보장되지는 않습니다.

**3.5 Checks — Write gate.** 세 단계로 실행합니다. 먼저 컴파일된 코드가 인수와 이전 도구 결과에서 확정적인 위반을 계산합니다. 다음으로 Kev가 정책·대화·날짜 주석과 정렬 정보를 붙인 도구 결과·현재 호출을 읽고 질문에 답합니다. 마지막으로 코드의 위반이 있거나 질문의 불리언 허용 규칙이 거짓이면 문제로 표시합니다.

쓰기 질문은 $`P(\mathrm{yes})\leq0.05`$일 때만 확신 있는 “아니오”로 처리하며, 그 밖에는 “예”로 취급합니다. 이 보수적인 개입 기준은 불확실할 때 자동 차단하는 규칙과 다릅니다. 피드백은 확인된 위반과 실패 질문을 열거하고, 호출 수정·추가 정보 요청·요청을 수행할 수 없는 이유 설명 중 적절한 대응을 요구합니다. 에이전트가 원래 호출이 맞다고 생각하면 재제출할 수도 있습니다. 두 번째 문제 표시 후에는 다시 도구를 부르기보다 사용자에게 답하라고 안내합니다.

**Hand-off check.** 전송 도구 호출과 포기 발언 앞에서 동작합니다. 발언은 먼저 키워드로 후보를 추린 뒤 판정 모델이 실제 포기인지 확인합니다. Kev는 어떤 문제 유형이 적용되는지, 사용자가 해결되었다고 확인했는지, 각 단계가 정리되었는지를 판단합니다. 어떤 단계가 필요한 문제일 확률이 0.5 이상이면서 그 단계가 정리되었을 확률이 0.5 이하이면 미완료 단계로 취급합니다. 문제가 해결되지 않았고 이런 단계가 하나라도 있으면 인계를 돌려보냅니다. 수정은 한 번만 허용합니다.

**Function calling without a policy.** BFCL에는 정책이 없으므로 고정된 두 검사를 사용합니다. 첫째, `needs to`·`must` 같은 요구를 담은 도구 오류가 해결되지 않았는데 턴을 마치려 하면, Kev가 그 요구를 해결할 도구를 고릅니다. 특정 도구가 맞을 확률이 0.6 이상이면 사용자에게 넘기기보다 해당 도구를 호출하라는 피드백을 줍니다. 둘째, 상태를 바꾸는 호출 앞에서 사용자가 요청했거나 도구 오류가 요구한 행동인지 묻습니다. “예” 확률이 0.05 이하이면 요청받지 않은 행동으로 표시합니다. 정책 기반 취소 자격 검사를 BFCL에도 그대로 쓴 것은 아닙니다. ### 📖 **Chapter 4: Experimental Setup**

**4.1 Benchmarks.** Airline의 50개 과제는 예약·취소·변경의 정책 준수를 평가합니다. Telecom은 114개 base-split 과제로, 도구 호출뿐 아니라 사용자의 기기 조작을 안내하는 문제 해결을 평가합니다. 두 도메인의 사용자 시뮬레이터는 GPT-4.1이고, 벤치마크 자체의 최종 데이터베이스 상태와 필수 의사소통 조건으로 채점합니다.

BFCL multi-turn은 base·missing function·missing parameter·long context에 각각 200개씩, 총 800개 항목입니다. 사용자 턴은 고정되어 시뮬레이터가 없습니다. 시스템 프롬프트 없이 사용자 턴당 최대 20단계의 함수 호출 루프를 따르며, 모든 턴의 최종 상태와 응답이 정답에 맞아야 항목을 성공으로 셉니다. 세 설정의 성공률을 같은 난도·같은 행동 유형의 점수로 해석하면 안 됩니다.

**4.2 Agent LLMs.** GPT-4.1, Opus 4.6, gpt-oss-20b·120b, Qwen3.8-27B, DeepSeek-V4-Pro는 세 설정 모두에 등장합니다. Haiku 4.5·Opus 5.5는 Telecom에만, Llama 3.3 70B·Mistral Small 3.2 24B·Gemma 4 31B는 BFCL에만 사용합니다. 비교 쌍의 에이전트 모델은 같고 하네스만 바뀝니다. 에이전트는 temperature 0, 최대 출력 4,096토큰이며 GPT-4.1 시뮬레이터도 temperature 0입니다.

**4.3 Judge and Compiler.** 기본 판정 모델은 모든 설정에서 Kev-27B이고, 정책 검사 컴파일러는 Claude Opus 4.6입니다. 쓰기 수정 2회·인계 수정 1회와 앞서 설명한 임계값을 사용합니다. 판정 모델 크기 실험에서는 Kev-27B로 정한 질문·임계값·제거 항목을 고정합니다. 반면 판정 모델 종류 비교에서는 대체 생성형 모델마다 무라벨 방식으로 제거할 질문 목록을 따로 정합니다. 따라서 두 실험을 순수한 모델 크기 비교 하나로 합칠 수 없습니다.

**4.4 Metrics.** 주 결과와 판정 모델 비교는 과제당 세 번 실행합니다. n번 중 c번 성공한 과제의 지표는 다음과 같으며, 이를 과제별로 계산해 평균합니다.

```math
\mathrm{pass@}k=1-\frac{\binom{n-c}{k}}{\binom{n}{k}},\qquad
\mathrm{pass}^{k}=\frac{\binom{c}{k}}{\binom{n}{k}}.
```

$`n`$은 실행 횟수, $`c`$는 성공 횟수, $`k`$는 묶어서 평가할 횟수입니다. 이 실험처럼 n=k=3이면 **pass@3은 세 번 중 한 번이라도 성공한 과제의 비율**, **pass^3은 세 번 모두 성공한 과제의 비율**입니다. pass^1은 개별 실행의 평균 성공률입니다. 서로 다른 과제를 세 개 푼다는 뜻도, 세 번 평균 점수가 pass^3이라는 뜻도 아닙니다. 예를 들어 한 과제를 세 번 중 두 번 성공하면 그 과제는 pass@3에는 포함되지만 pass^3에는 포함되지 않습니다.

**4.5 Checks Per Benchmark.** Airline과 Telecom은 각각 6개 쓰기 도구에 86개·75개 질문을 생성하며, 그중 17개·5개를 제거합니다. Telecom에는 8개 문제 유형의 인계 체크리스트도 붙이고 7개 단계를 제거합니다. Airline의 인계 검사는 해결된 에피소드에서도 26%를 문제로 표시해 비활성화했습니다. 어떤 도메인에서 잘못 개입하는 검사를 끄는 설정 역시 최종 결과의 일부입니다. [4절·Table 1](https://arxiv.org/html/2610.38620v1#S4)

GPT-4.1 에이전트에서 무조건 재검토는 pass^3 26→28%, 전체 게이트는 26→40%였으며, 전체 게이트의 ReAct 대비 차이에 대한 짝지은 95% 신뢰구간은 +2.0~+26.0%p입니다. 반면 에이전트까지 gpt-oss-120b이면 재검토만 하거나 게이트와 같은 빈도로 무작위 문제 표시를 해도 전체 게이트와 같은 32→42% 개선이 나옵니다. **추가 수정 기회 이상의 효과가 있는지는 에이전트에 따라 달랐습니다.** 이 실험을 주 결과의 GPT-4.1 사용자 시뮬레이터 조건과 섞어서는 안 됩니다.

**Overall findings.** 저자들은 코드 검사의 큰 기여, 생성형 심사와 경쟁력 있는 결정 모델의 추정 비용, 작은 모델도 유효할 수 있는 조건을 묶습니다. 핵심은 “Kev가 항상 우월하다”가 아니라, 기록 계산과 대화 판단을 모듈로 나눠 검증할 수 있다는 것입니다. [5절](https://arxiv.org/html/2610.38620v1#S5)

### 📖 **Chapter 6: Conclusion**

결론은 선택적 실행 전 검사와 한정된 수정 기회를 전체 하네스로 정리합니다. 주 조건에서 Telecom은 일관된 개선, BFCL은 세 번 모두 성공률의 개선, Airline은 작은 혼합 결과를 보입니다. 이를 모든 도메인의 일률적 개선이나 판정 모델만의 인과 효과로 해석하지 않습니다.

저자가 명시한 주의 조건은 두 가지입니다. **사용자 시뮬레이터를 gpt-oss-120b로 바꾸면 Telecom의 개선이 재현되지 않습니다.** pass^3 차이는 −1.8%p, 95% 신뢰구간은 −7.9~+4.4%p입니다. 또 라벨된 개발 쓰기 호출 260개 중 잘못된 호출 101개를 보면, 그중 42개는 컴파일된 질문을 하나도 어기지 않습니다. 정책을 질문으로 바꿨다고 사용자의 구체적인 요청까지 빠짐없이 포착한 것은 아니라는 원문의 설명입니다.

**Future work.** 원문이 제안하는 후속 방향은 ReAct 외 에이전트 구조에 공통 행동·상태·실행 결과 인터페이스를 적용하는 것, 정책·스키마에서 검사 생성과 코드 검증을 더 자동화하는 것, 보류한 실행 기록으로 임계값과 수정 예산을 정하는 것입니다. 오탐과 누락을 함께 다루고 불확실하거나 영향이 큰 판단에는 사람에게 넘길 경로를 유지하자고 제안합니다. 더 넓은 도메인과 프레임워크에서 종단 간 지연·비용·안전 결과를 과제 성공·반복성 지표와 함께 보고하자는 내용도 포함합니다. 이는 저자의 후속 계획이며 이 리뷰에서 새로 만든 한계 목록이 아닙니다. Kev-9B의 짧은 입력 임계값을 0.05에서 0.10으로 바꾸면 오탐을 추가하지 않고 8개에서 16개를 탐지합니다. 긴 입력에서는 최적 임계값으로도 32개 중 2개만 잡습니다. Kev-0.8B는 짧은 입력에서도 AUROC가 낮습니다. 원문 Table 8은 27B와의 AUROC 차이에 95% 신뢰구간도 제공합니다. 짧은 입력에서 9B는 −0.15~+0.04, 0.8B는 −0.23~−0.02이며, 긴 입력은 각각 −0.37~−0.12, −0.50~−0.19입니다.

라벨로 각 모델의 가장 좋은 임계값을 찾은 결과는 실제 무라벨 배치 성능이 아니라 라벨을 이용한 상한 비교입니다. Table 8은 “Kev-27B의 오탐 수 이하”라는 조건으로 표를 설명하지만, 짧은 입력 Kev-0.8B의 최적 행에는 탐지/오탐 8/1이 적혀 있어 Kev-27B의 21/0과 맞지 않는 부분도 있습니다. 이 리뷰는 그 행으로 무오탐 보장을 주장하지 않고, 기본 임계값의 결과와 9B 보정 사례를 구분합니다. [A.4·Table 8](https://arxiv.org/html/2610.38620v1#A1.SS4)

**A.5 Token usage.** Table 9는 에피소드당 평균 토큰을 천 단위로 보고합니다. Airline의 GPT-4.1은 ReAct 입력/출력 58.4/0.9천 토큰, JevAct 60.1/0.9천 토큰, Kev 입력 9.0천 토큰이며 되돌린 초안은 에피소드당 0.39개입니다. Telecom의 같은 모델은 130.6/1.2에서 167.3/1.4천 토큰으로 늘고 Kev 입력 16.8천 토큰, 되돌린 초안 1.44개입니다. 검사가 저렴해도 추가 문제 해결로 에이전트 토큰이 늘 수 있음을 보여 줍니다.

## 실험 결과 심층 분석

가장 뚜렷한 결과는 **주 설정에서 반복 성공률이 개선된 것**입니다. Telecom의 8종 모두 pass@3과 pass^3이 높아졌고, BFCL의 9종 모두 pass^3이 올랐습니다. 하지만 BFCL에서는 더 적은 과제를 한 번이라도 풀게 된 모델도 5종입니다. 안정적으로 푸는 과제의 비율과 도전할 수 있는 과제 범위는 다른 축입니다. Airline은 실패한 결과까지 함께 있어 “실행 전 검사만 붙이면 항상 좋아진다”는 결론을 지지하지 않습니다.

인과 효과를 읽을 때도 구분이 필요합니다. 같은 에이전트 모델을 쓴 비교는 모델 교체 효과를 배제하지만, 코드 검사·결정 모델·검사 대상 선택·수정 호출의 효과를 모두 분리한 것은 아닙니다. 단일 시행의 구성 요소 실험과 별도 시뮬레이터의 재검토 대조군은 그 구분을 돕습니다. gpt-oss-120b 에이전트에서는 재검토 자체로 전체 게이트만큼 개선된다는 결과가 특히 중요합니다. 큰 개선 수치만으로 Kev의 판정 능력이 원인이라고 결론 내릴 수 없습니다.

통계 정보도 보고 범위를 나눠 읽어야 합니다. Table 2의 모델·설정별 주 점수에는 신뢰구간이나 유의성 검정이 보고되지 않았습니다. 반면 별도 대조 실험의 짝지은 차이, 시뮬레이터 변경 결과, Table 8의 AUROC 차이에는 95% 신뢰구간이 제시됩니다. 과제당 3회 실행이라는 사실 자체가 모든 차이의 통계적 유의성을 입증하지는 않습니다. 특히 Airline은 50과제로 점수의 한 칸이 2%p입니다.

재현 관점에서 원문은 임계값·수정 예산·컴파일 프롬프트·제거 기준·판정 모델과 컴파일러·토큰 집계·비용 가정을 상세히 제공합니다. 동시에 Telecom 체크리스트의 결과 검토 후 수정, 일부 BFCL 요청의 재구성 누락, 반려 초안 토큰 미기록도 밝힙니다. 이 리뷰는 논문 HTML·PDF와 제시된 예시를 분석했으며 벤치마크를 직접 재실행한 결과를 포함하지 않습니다.

## 기술적 함의와 응용

JevAct를 통해 배울 수 있는 설계 원리는 **자연어 판단과 구조화된 기록의 계산을 같은 도구로 밀어 넣지 않는 것**입니다. 날짜 비교나 수량 계산은 코드로 확정하고, 사용자 의도와 절차 수행은 좁은 질문으로 나눠 독립 판정을 받습니다. 리뷰어의 해석으로는 예약 변경·계정 설정·고객 지원처럼 기록과 대화가 함께 필요한 작업에서 이 분업을 검토할 가치가 있습니다. 이 논문이 모든 산업 업무에서 동일한 이득을 검증했다는 뜻은 아닙니다.

다른 하나는 검사를 **제어 흐름 전체로 이해해야 한다는 점**입니다. 어떤 호출을 검사하는가, 오탐 질문을 어떻게 제거하는가, 피드백을 어디까지 보존하는가, 언제 수정 시도를 끝내는가가 모두 결과를 결정합니다. 이 논문의 게이트는 예산 소진 뒤 실행을 허용하고, 정책을 표현한 질문이 사용자의 요청을 빠뜨릴 수도 있습니다. 그러므로 관찰된 성공률 개선과 무조건적인 정책 준수 보장은 별개입니다. JevAct의 성과는 이 구체적인 실행·평가 조건 아래에서, 계산 가능한 사실과 대화 판단을 나눈 선택적 검증이 에이전트 행동을 개선할 수 있음을 보여 준 데 있습니다.
