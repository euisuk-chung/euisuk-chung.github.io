## 들어가며: 모델을 여러 번 돌리면 생성도 그만큼 느려질까요?

같은 Transformer 층을 여러 번 통과시키면, 가중치를 더 늘리지 않고도 토큰 하나에 더 많은 계산을 쓸 수 있습니다. 이를 **루프형 언어모델(looped LM)**이라고 합니다. 다만 같은 모델을 네 번 통과한다면, 토큰을 하나 생성할 때 기다려야 하는 계산도 늘어납니다. 각 반복의 과거 정보를 따로 저장하는 KV 캐시까지 유지하면, 가중치에서 아낀 메모리를 캐시가 차지할 수 있습니다.

**2DSD는 다음 토큰들을 미리 준비하는 추측 디코딩을, 토큰 방향과 반복 깊이 방향에 함께 적용합니다.** 얕은 반복에서 얻은 예측으로 다음 블록을 준비하는 동안 앞선 토큰의 나머지 반복을 계산하고, 마지막 반복의 분포로 실제 출력을 확정합니다. 여기에 오래된 KV 캐시를 반복 사이에서 공유하는 방식을 결합합니다.

이 글은 [SqueezeAILab/2DSD의 고정 커밋](https://github.com/SqueezeAILab/2DSD/tree/431aade2f1e8ebc98a31158d53c39e554984a83a)과 레포 안의 [22쪽 논문](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/paper/2DSD.pdf)을 함께 읽습니다. 논문의 알고리즘과 실험 조건을 먼저 이해하고, 그 절차가 코드에서 어떤 데이터와 분기로 구현됐는지 따라가겠습니다. 코드·모델·테스트는 실행하지 않았으며, 성능 수치는 저자들의 보고 결과입니다. README의 2026년 11월 19일은 코드와 모델 공개 안내일입니다. 이를 논문 제출일이나 학회 채택일로 바꾸어 쓰지는 않았습니다.

## 무엇인가: 두 축의 추측과 하나의 최종 판단

일반적인 자동회귀 생성(AR)은 앞부분이 확정돼야 다음 토큰을 생성합니다. 토큰은 모델이 글을 처리하는 작은 단위입니다. **추측 디코딩(speculative decoding)**은 저렴한 초안 모델(drafter)이 여러 토큰을 제안하고, 실제 서비스할 목표 모델(target)이 이를 검증하게 해 생성 속도를 높입니다.

루프형 모델에는 또 다른 기회가 있습니다. 토큰이 전체 반복을 마치기 전에도 중간 상태에서 다음 토큰을 예측할 수 있기 때문입니다. 2DSD의 두 축은 다음처럼 구분됩니다.

| 축 | 미리 하는 일 | 최종적으로 확인할 것 |
| --- | --- | --- |
| 토큰 축 | 앵커 뒤의 여러 토큰을 한 블록으로 제안 | 목표 모델의 다음 토큰 분포와 맞는지 |
| 깊이 축 | 앞선 토큰의 반복이 끝나기 전에, 얕은 반복 예측으로 다음 계산 시작 | 마지막 반복에서 얻은 분포와 맞는지 |

여기서 반복은 프롬프트를 다시 보내거나 답변 문장을 여러 번 고치는 절차가 아닙니다. **한 토큰의 은닉 상태가 공유된 신경망 층을 여러 번 통과하는 계산**입니다. 논문은 전체 Transformer 스택을 반복하는 Ouro·Nanbeige와, 중간 블록을 반복하는 Dory를 다룹니다. [논문 2–4절](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/paper/2DSD.pdf#page=2)

중요한 경계도 있습니다. 추측 디코딩의 출력 보존은 **서비스하는 목표 모델의 분포**를 기준으로 합니다. KV 공유를 위해 Ouro를 추가 학습했다면, 그 추가 학습된 모델의 출력을 보존한다는 뜻입니다. 원래 체크포인트와 추가 학습된 체크포인트의 응답까지 완전히 같다는 주장은 아닙니다.

## 아키텍처: vLLM 위에 별도 실행기를 얹습니다

레포에는 사용자가 호출하는 스크립트, 모델 설정, vLLM 포크, 학습 코드가 함께 들어 있습니다. 여기서 worker는 GPU 모델 계산을 맡는 작업 프로세스이고, RPC는 그 프로세스에 작업을 보내는 호출입니다. Prefix는 확정된 앞부분, tree는 아직 검증할 후보 갈래를 가리킵니다.

| 경로 | 이 글에서 확인한 역할 |
| --- | --- |
| `scripts/generate.py` | 모델·프롬프트·생성 설정을 해석하고 결과 출력 |
| `configs/models.json`, `training/common/registry.py` | 모델 별칭을 target·drafter·revision·KV 정책으로 해석 |
| `vllm-fork/.../spec_decode/twodsd.py` | 공개 Python API와 worker RPC 진입점 |
| `vllm-fork/.../spec_decode/looped_2d_finalized.py` | 후보 트리, 중간 검토, 승격·분기, 최종 검증·확정 |
| `vllm-fork/.../models/ouro_tree.py`, `ouro_finalized.py` | Ouro의 prefix/tree KV와 실행 상태·저장 공간 관리 |
| `vllm-fork/.../models/looped_kv.py` | 공유 KV 정책과 지원 조건 검증 |
| `scripts/benchmark.py` | 생성 기록과 decode 처리량·반복 응답 필터 집계 |
| `training/kd/`, `training/sharekv/`, `training/drafter/` | 공유 KV 적응과 깊이 조건부 초안 모델 학습 |

`TwoDSD`는 vLLM 엔진을 가중치 로드에 사용하고, `collective_rpc("run_2dsd", ...)`로 worker 안의 전용 실행기를 호출합니다. 이 실행기는 **vLLM의 기본 스케줄러나 paged KV 캐시에 생성 스케줄을 맡기지 않습니다.** 자신의 prefix/tree KV를 관리합니다. 모델별 runner가 실제 신경망 계산을 담당하고, executor가 어떤 후보를 다음 반복으로 진행시킬지 결정하는 구조입니다. ## 작동 원리: 초안에서 확정 토큰까지

### 1. 별칭을 해석하고 생성 예산을 정합니다

`generate.py`는 `registry.serving()`으로 모델 별칭과 `--target`을 해석합니다. 기본값 `w64`는 공유 KV 목표 모델을 선택하며, `original`은 원래 모델과 그에 맞는 drafter를 선택합니다. Dory는 별도의 적응 체크포인트 대신 같은 고정 체크포인트에 반복 수·KV 정책을 덮어씁니다. 이후 채팅 템플릿을 적용하고 토큰화한 프롬프트를 `engine.generate()`에 전달합니다. [CLI](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/scripts/generate.py#L38-L95), [레지스트리 해석](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/training/common/registry.py#L67-L105)

`max_total_tokens`는 프롬프트와 출력의 합계 예산입니다. `TwoDSD.generate()`는 각 요청의 출력 예산을 계산하고, worker는 짧은 워밍업 뒤 요청들을 순서대로 실행합니다. **여러 프롬프트를 리스트로 받는다고 여러 요청을 동시에 배치 처리하는 API는 아닙니다.** 코드 설명대로 한 GPU·배치 크기 1의 생성 경로입니다. [요청 생성](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/vllm-fork/vllm/v1/spec_decode/twodsd.py#L293-L354), [워밍업과 결과 회수](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/vllm-fork/vllm/v1/spec_decode/twodsd.py#L105-L169)

### 2. 토큰마다 완료한 반복 수와 후보 상태를 남깁니다

주 설정은 전체 반복 수 `R=4`, 얕은 검토 `r₁=1`, 깊은 분기 `r₂=2`, 블록 크기 `k=16`입니다. Nanbeige는 `R=2`이므로 첫 반복에서 초안을 준비하는 early-only 설정을 씁니다. [모델별 preset](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/vllm-fork/vllm/v1/spec_decode/twodsd.py#L172-L179)

`FinalizedNode`는 토큰, 부모, 절대 위치, 완료한 반복 수 `depth`, 반복별 readout, 후보 역할, 제안 분포를 저장합니다. 후보 역할은 기본 경로인 `main`, 중간 검토에서 거절됐지만 남겨 둔 `frozen`, 깊은 예측에서 추가한 `fork`입니다. **트리의 노드는 확정된 출력이 아니라, 앞부분과 연결된 계산 후보**입니다. [후보 자료구조](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/vllm-fork/vllm/v1/spec_decode/looped_2d_finalized.py#L43-L79)

프롬프트를 prefill한 뒤 마지막 분포에서 첫 토큰을 선택합니다. 이 토큰이 블록의 앵커이고, drafter가 뒤의 `k−1`개 토큰을 제안합니다. 반복 루프는 아직 `R`에 도달하지 않은 후보들을 모아 한 반복씩 진행시킵니다. 후보들이 서로 다른 깊이에 있어도 같은 target 호출에서 계산을 겹칠 수 있습니다. [초기화와 전진](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/vllm-fork/vllm/v1/spec_decode/looped_2d_finalized.py#L986-L1140)

### 3. 얕은 반복에서 틀렸다고 바로 버리지는 않습니다

`r₁`에 도달하면 앵커 뒤의 초안들을 순서대로 검토합니다. Greedy에서는 직전 토큰의 얕은 readout이 선택한 토큰과 초안이 같은지 확인합니다. 첫 불일치가 나오면 그 위치에서 새 앵커를 만들고 뒤의 블록을 다시 준비합니다.

다만 거절된 꼬리는 즉시 삭제하지 않습니다. `frozen`으로 남겨 나머지 반복을 계산하게 합니다. 얕은 예측과 맞지 않았더라도 마지막 반복에서는 맞을 수 있기 때문입니다. frozen 상태에서는 추가 중간 검토와 초안 생성을 멈추지만, 최종 검증의 후보 자격은 유지합니다. [초안 검토와 첫 거절](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/vllm-fork/vllm/v1/spec_decode/looped_2d_finalized.py#L294-L345), [논문 Appendix B](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/paper/2DSD.pdf#page=12)

### 4. 더 깊은 예측이 다르면, 남긴 후보를 승격하거나 갈래를 만듭니다

`r₂`에서는 가장 가능성이 높은 토큰이 얕은 단계의 main 후보와 다른지 봅니다. 이것이 기본 **argmax gate**, 즉 가장 높은 확률의 토큰을 비교해 여는 분기 조건입니다. Sampling에서도 이 gate는 대안을 만들지 결정할 뿐, 최종 출력 토큰을 직접 확정하지 않습니다.

깊은 예측이 앞서 frozen으로 남긴 토큰과 같으면, 그 토큰과 꼬리를 **승격(promotion)**합니다. 이미 끝낸 반복 계산을 다시 하지 않고 후속 검토·초안 생성을 재개합니다. 일치하는 frozen 후보가 없으면 새로운 **분기(fork)**를 준비합니다. Sampling의 fork는 깊은 분포와 얕은 분포의 양의 차이를 바탕으로 뽑으며, 같은 위치에서 이미 제안한 토큰은 제외합니다. [Greedy 분기](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/vllm-fork/vllm/v1/spec_decode/looped_2d_finalized.py#L347-L388), [Sampling 분기](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/vllm-fork/vllm/v1/spec_decode/looped_2d_finalized.py#L603-L717)

대안이 늘면 성공할 후보를 미리 계산할 가능성은 커집니다. 반대로 drafter 호출과 후보 계산·저장 비용도 늘어납니다. 실제 부록 E.6에서는 Ouro-1.4B에 early-only `r₁=2`가 가장 빠르며, 모든 모델에서 깊은 분기가 항상 최선은 아닙니다. 코드의 기본 preset과 특정 ablation의 최적값을 구별해야 합니다. [논문 Table 11과 진단](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/paper/2DSD.pdf#page=21)

### 5. 마지막 반복의 분포로 출력할 토큰을 확정합니다

확정에는 **직전 토큰의 마지막 반복 분포**를 사용합니다. 다음 후보 토큰이 자기 반복을 모두 마쳤는지만 보고 출력하는 것이 아닙니다. Greedy에서는 그 분포의 argmax와 같은 다음 토큰을 고르고, 맞지 않는 형제 가지를 정리합니다. 이미 계산한 올바른 경로는 재사용합니다. [Greedy 최종 검증](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/vllm-fork/vllm/v1/spec_decode/looped_2d_finalized.py#L390-L463)

Sampling에서는 후보를 `main → frozen → fork` 순서로 검증합니다. 현재 목표 분포를 $`P`$, 후보를 뽑았을 때의 기록된 제안 분포를 $`Q`$, 제안 토큰을 $`y`$라 하면 수락 확률은 다음과 같습니다.

```math
\alpha(y)=\min\left(1,\frac{P(y)}{Q(y)}\right).
```

이는 **제안된 토큰을 조건으로 한 수락 확률**입니다. 거절했다면 같은 $`P`$에서 다음 후보를 검사하지 않습니다. 양의 차이만 남긴 잔여 분포로 목표 분포를 갱신합니다.

```math
\begin{aligned}
P'(v)&=\frac{[P(v)-Q(v)]_+}{Z},\\
Z&=\sum_u[P(u)-Q(u)]_+.
\end{aligned}
```

$`[a]_+`$는 $`\max(a,0)`$입니다. $`Z`$는 남은 확률 질량을 합해 분포를 다시 정규화하는 값이며, 거절이 발생할 수 있는 잔여 질량이 있을 때의 식입니다. 원문 식 (2), (5), Appendix B의 잔여 보정을 설명용 기호 $`P'`$와 $`Z`$로 나누어 썼습니다. 이 절차를 각 후보에 반복하고, 전부 거절되면 최종 잔여 분포에서 새 토큰을 뽑습니다. [논문 4.1절과 도출](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/paper/2DSD.pdf#page=4)

논문은 “수락해 출력되는 질량”과 “거절 후 보정해 출력되는 질량”을 더하면 원래 목표 확률 $`P(v)`$가 된다는 관계로 분포 보존을 설명합니다. 후보가 그럴듯하다는 이유만으로 출력하는 방식과 다른 지점입니다. 이 보존은 매 단계에서 **실제로 사용한 제안 분포를 기록하고, 거절 뒤에 목표 분포를 보정하는 조건**에 의존합니다. Sampling에서 같은 seed로 Native AR과 문자 그대로 같은 응답을 낸다는 뜻도 아닙니다.

아래는 실제 `_verify_sampled()`에서 후보 거절 후 잔여 분포를 만드는 부분입니다. `proposal is None`은 현재 구현의 one-hot argmax 초안을 나타내므로 그 토큰의 질량만 0으로 만듭니다. 일반 제안 분포가 있으면 목표에서 이를 빼고 양수만 남깁니다.

```python
if proposal is None:
    rest = target.clone()
    rest[child.token] = 0
else:
    rest = (target - proposal).clamp_min_(0)
target = _normalized(rest, target)
```

### 6. 오래된 KV는 공유하고, 최근 계산은 따로 유지합니다

KV 캐시는 앞서 처리한 토큰의 key·value를 저장해 attention 계산에서 다시 쓰는 메모리입니다. 반복마다 별도 캐시를 읽으면, 서로 다른 반복의 질의를 한 번에 계산해도 과거 캐시는 각각 읽어야 합니다. 2DSD는 오래된 확정 토큰에 대해 마지막 반복의 캐시를 공유하고, 최근 `W`개 위치는 반복별 캐시를 유지합니다.

![Native 모델은 각 반복의 이력 KV를 유지하고 Shared-KV는 마지막 반복의 이력 KV를 공유하며 최근 W 위치의 반복별 캐시는 남기는 비교]({{ '/img/reviews/2026/2dsd-review/figure4-kv-sharing.png' | relative_url }})

마지막 반복의 이력 KV를 공유하되 최근 창은 따로 남기는 구조입니다. Kim 외, [2DSD Figure 4](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/paper/2DSD.pdf#page=5), PDF 5쪽의 도식 영역만 크롭한 해설용 인용입니다. 원문 표기·범례를 유지했습니다.
{: .caption}

논문의 기본 읽기 규칙은 다음과 같습니다. $`t`$는 현재 질의 위치, $`j`$는 참조하는 과거 위치, $`r`$은 현재 반복, $`R`$은 마지막 반복입니다.

```math
\mathrm{Read}_r(t,j)=
\begin{cases}
C^{(R)}_j,&j\leq t-W,\\
C^{(r)}_j,&t-W\lt j\leq t.
\end{cases}
```

$`C^{(r)}_j`$는 위치 $`j`$에서 반복 $`r`$이 만든 KV입니다. 공유 구간과 최근 창은 하나의 softmax attention으로 결합합니다. 최근 토큰은 아직 마지막 반복을 끝내지 않았을 수 있으므로, 전부 마지막 반복 캐시만 읽도록 바꾸면 앞선 토큰을 기다려야 합니다. **최근 창을 남기는 이유는 깊이 방향의 동시 진행을 유지하기 위해서**입니다. [논문 식 (6)과 설명](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/paper/2DSD.pdf#page=5)

이 기본 규칙에는 모델별 예외가 있습니다. Ouro·Nanbeige는 첫 반복의 첫 층에서 native KV를 유지합니다. 토큰 임베딩으로 만든 첫 층의 KV가 이후 반복과 다르기 때문입니다. Dory는 입력 블록의 native KV를 유지하고 full-attention 층에만 공유를 적용하며, 이미 1024토큰 창으로 제한되는 sliding-window attention에는 공유를 적용하지 않습니다. [정책 코드 설명](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/vllm-fork/vllm/model_executor/models/looped_kv.py#L1-L24), [논문 Appendices C·D.1](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/paper/2DSD.pdf#page=15)

주 설정은 `W=64`입니다. 코드의 `check_tree_window()`는 진행 중인 토큰 범위를 담을 수 있도록 `R × k ≤ W`를 검사합니다. `R=4`, `k=16`이면 64이므로 이 창 안에 들어갑니다. 단순 메모리 절약 옵션이 아니라 계산 순서를 성립시키는 조건입니다. [창 크기 검사](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/vllm-fork/vllm/model_executor/models/looped_kv.py#L158-L170)

### 7. KV 공유 적응과 drafter 학습은 별개입니다

Ouro·Nanbeige는 원래 반복별 KV를 쓰던 모델을 공유 KV 목표 모델로 적응시킵니다. 논문 부록 C는 frozen teacher의 출력 분포를 따라가도록 하는 자기 증류(self-distillation)를 설명합니다. 학생의 첫 pass는 gradient 없이 native attention을 계산하고 마지막 반복 KV를 남깁니다. 두 번째 pass는 그 KV를 공유 이력으로 사용하면서 학습합니다. Prompt는 native 방식이며, 마지막 반복과 첫 반복 첫 층의 예외도 유지합니다. 이 **두 pass 근사는 학습에 쓰는 절차**로, 추론 때 매번 두 번 prefill한다는 뜻이 아닙니다.

`k2_forward()`는 no-grad 참조 KV와 학습 pass를 연결하고, `full_forward_kl()`는 teacher와 student 사이의 full-vocabulary forward KL을 계산합니다. 논문이 보고한 적응은 128M 토큰·한 epoch이며 4장 H100에서 Ouro-1.4B 3.4시간, Ouro-2.6B 6.7시간, Nanbeige 4.0시간입니다. [두 pass 구현](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/training/sharekv/rule.py#L194-L235), [KL 구현](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/training/kd/loss.py#L8-L13), [논문 Appendix C](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/paper/2DSD.pdf#page=15)

Drafter는 별도로 학습합니다. 논문에서는 고정한 목표 모델의 embedding·LM head와 다섯 층의 DFlash drafter를 사용합니다. 확정 토큰의 마지막 반복 특징과 진행 중인 토큰의 현재 반복 특징을 조합해 다음 블록을 제안합니다. 13K 프롬프트의 target rollout을 준비하고 여섯 epoch 학습하는 절차이며, 공유 KV 적응과 데이터·목표·역할이 다릅니다. Dory는 공유 KV 적응 없이 동작하지만 **drafter 학습까지 필요 없다는 뜻은 아닙니다.** [학습 파이프라인](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/training/README.md#L1-L17), [논문 Appendix D.4](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/paper/2DSD.pdf#page=17)

### 8. 성능표는 어떤 조건의 속도인지 함께 읽습니다

주 처리량 평가는 **H100 NVL 한 장, batch size 1, BF16**, 블록 크기 16, `R=4`, `(r₁,r₂)=(1,2)`, `W=64` 조건입니다. Table 5의 하드웨어 비교와 Table 11의 ablation은 **Core 고정 64문항, 벤치마크별 16개**이므로 전체 주 평가와 동일한 표본으로 읽으면 안 됩니다. [논문 Appendix D.2–D.3](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/paper/2DSD.pdf#page=17)

**Nanbeige는 중요한 반례입니다.** `R=2`에서는 2DSD의 unfiltered 기하평균 배수가 greedy 2.37×, sampling 2.01×로, DFlash의 3.17×·2.86×보다 낮습니다. 겹칠 반복이 적고 첫 반복 argmax와 마지막 반복 argmax의 일치율도 49.8%로 낮습니다. 같은 진단의 Ouro는 91.0%·93.0%, Dory는 94.0%입니다. 논문은 이 차이를 깊이 방향 추측의 이득과 연결합니다. 이 결과까지 보면 “두 축을 합치면 모든 모델에서 더 빠르다”고 일반화할 수 없습니다. [논문 Appendix E.1, Tables 7–8](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/paper/2DSD.pdf#page=17)

KV 공유가 품질을 완전히 동일하게 유지한 것도 아닙니다. Table 3에서 Ouro-2.6B의 Hard 평균은 native 58.49%, 적응한 Shared-KV 57.06%이고, Ouro-1.4B는 50.95%에서 49.41%입니다. Core에서는 각각 76.92→79.02%, 76.03→76.17%입니다. Dory는 추가 적응 없이 Core 78.81→79.55%, Hard 76.34→77.06%를 기록합니다. **분포 보존 알고리즘과, 캐시 구조를 바꾼 모델의 품질 비교는 다른 실험**입니다. [부록 Table 9](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/paper/2DSD.pdf#page=20)의 Nanbeige에서는 적응 없이 공유했을 때 GSM8K 0.15%, 나머지 여섯 항목 0.00%로 품질이 거의 무너집니다. 공유를 켜는 것만으로 품질이 유지된다고 가정할 수 없는 사례입니다. [논문 Table 3](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/paper/2DSD.pdf#page=7)

메모리도 비교군을 확인해야 합니다. Ouro-2.6B의 16K 문맥에서 총 peak GPU 메모리는 native AR 35.3GB에서 2DSD 21.4GB로 줄고, 확정 KV는 27.4GB에서 7.1GB로 줄었습니다. 그러나 공유 KV를 쓰는 DFlash 18.9GB, LoopSpec 17.0GB보다는 큽니다. 후보·drafter·CUDA graph 등 부가 저장량이 있기 때문입니다. “메모리를 가장 적게 쓰는 방법”이라는 결론은 이 그림과 맞지 않습니다. L40S·A100에서도 이득을 보고했지만, 그 하드웨어 표의 표본 범위는 앞서 구분한 64문항입니다. [논문 Figure 7·Table 5](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/paper/2DSD.pdf#page=8)

## 설치와 사용: 공식 명령을 읽을 때의 전제

README는 Linux x86_64, Python 3.12, BF16을 지원하는 NVIDIA GPU와 CUDA 13.0을 지원하는 드라이버, `uv`를 요구합니다. `pyproject.toml`은 로컬 `vllm-fork`를 `vllm==0.26.0+2dsd`로 사용하도록 합니다. **기존 vLLM에 Python 클래스 하나만 추가하는 설치가 아니라 포크된 실행 경로를 포함하는 환경**입니다. [설치 안내](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/README.md#L32-L42), [의존성 설정](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/pyproject.toml#L1-L42)

아래는 같은 커밋 README의 명령입니다. 이 리뷰에서 실행하지 않았습니다.

```bash
git clone https://github.com/SqueezeAILab/2DSD.git
cd 2DSD
uv sync --locked --no-editable
source .venv/bin/activate
python scripts/generate.py --model ouro-2.6b-thinking --prompt "What is the sum of the first 100 positive integers?"
```

[README의 설치·생성 예시](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/README.md#L32-L66)를 순서대로 정리했습니다. 이 명령의 clone은 현재 기본 브랜치를 받으므로 이 글의 고정 SHA를 자동으로 재현하는 명령은 아닙니다. 원래 target을 선택하려면 문서의 `--target original`을 사용합니다.

레지스트리는 base 모델 revision을 고정하지만 공유 KV target과 drafter 일부는 revision 없는 Hugging Face ID입니다. 따라서 **코드 SHA가 같다는 것과 앞으로 내려받을 모든 가중치 버전이 고정됐다는 것은 별개**입니다. 코드에서 `--revision`, `--drafter` 등으로 override할 수 있는 범위와 모델 출처를 함께 확인해야 합니다. [모델 목록](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/configs/models.json#L1-L49), [revision 해석](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/training/common/registry.py#L41-L105)

## 한계와 주의점: 무엇을 그대로 보존하는가

이 구현의 범위는 지원하는 루프형 target과 깊이 조건부 drafter, 한 GPU·배치 크기 1의 실행입니다. 기본 설정은 입력 전체를 native 방식으로 prefill하고 별도 tree KV를 운영합니다. 장문 입력의 prefill 비용이나 다중 사용자 serving 지연을 포함한 결과로 주 decode 배수를 확장해서는 안 됩니다. [API 경계](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/vllm-fork/vllm/v1/spec_decode/twodsd.py#L181-L205), [지원 KV 설정](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/vllm-fork/vllm/model_executor/models/looped_kv.py#L92-L170)

추가 후보가 늘면 더 많은 계산과 메모리가 필요합니다. `NativeOuroFinalizedRunner`는 처음 할당한 노드 수를 확률 기반 가지치기 예산으로 쓰지 않고 물리 저장 공간을 늘립니다. 할당 실패 때 후보를 몰래 버려 출력을 바꾸는 경로로 설명하지 않습니다. 실제 메모리 한계와 실행 성공은 환경에서 별도로 확인해야 합니다. [용량 확장 계약](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/vllm-fork/vllm/model_executor/models/ouro_finalized.py#L18-L30)

테스트 디렉터리에는 가짜 runner와 확률 체인을 이용해 스케줄·sampling을 검사하는 코드, CUDA·graph 검사가 있습니다. 이는 검증 의도가 코드로 제공된다는 뜻이며, 이 글에서 테스트 통과나 실제 GPU 수치 재현을 확인했다는 뜻은 아닙니다. 주 성능표에는 신뢰구간·유의성 검정이 보고되지 않아 근소한 차이를 통계적으로 확정된 우열로 표현하지 않았습니다.

코드는 [Apache-2.0](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/LICENSE)이며 원본 발췌의 저작권·라이선스를 표시했습니다. README는 공개 가중치에 대해 Ouro·Nanbeige target/drafter는 Apache-2.0, Dory drafter는 OpenMDW License 1.1이라고 구분합니다. **코드와 모든 가중치·논문 그림이 하나의 동일한 라이선스라고 가정하지 않습니다.** 논문 그림은 출처·쪽수·크롭 범위를 명시한 최소 해설용 인용으로 사용했습니다. [README 라이선스 구분](https://github.com/SqueezeAILab/2DSD/blob/431aade2f1e8ebc98a31158d53c39e554984a83a/README.md#L165-L169)

## 결론: 두 축의 추측을 최종 검증으로 연결합니다

2DSD의 원리는 먼저 만든 초안을 그대로 내보내는 데 있지 않습니다. 얕은 반복에서 미래 토큰을 준비하고, 남겨 둔 후보의 계산을 재사용하며, 마지막 반복의 분포로 출력을 확정하는 흐름이 함께 있어야 합니다. KV 공유는 오래된 확정 이력과 최근 진행 중인 계산을 나눠, 메모리와 읽기 비용을 줄이는 다른 축입니다.

레포에서 특히 연결해 볼 부분은 `generate.py`의 target 선택, worker의 전용 executor, 후보별 제안 분포와 역할, 최종 검증 뒤 prefix 확장입니다. 이 연결을 따라가면 속도 향상과 출력 보존이 같은 이유로 성립하는 것이 아니라, 서로 다른 조건을 지키며 결합된다는 점이 분명해집니다.

### 이 글에서 다루지 못한 부분

논문 본문 1–7절과 부록 A–E를 읽고, 모델 해석·공개 API·Ouro 중심의 전용 executor와 KV 정책·대표 학습/평가 경로를 정적으로 대조했습니다. 원문 표의 모든 행, 모든 CUDA/Triton kernel·graph capture·Dory/Nanbeige runner의 전체 내부 구현·학습 데이터 처리의 전 경로를 개별 검증한 것은 아닙니다. 모델 다운로드·추론·학습·테스트와 독립 성능 재현은 수행하지 않았습니다.
