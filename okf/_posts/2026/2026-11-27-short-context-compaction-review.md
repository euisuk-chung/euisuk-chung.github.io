## 논문 개요와 전체 구조

코딩 에이전트가 오래 일할수록 이전 대화도 길어집니다. 그렇다면 오래 일하는 능력은 긴 대화창을 한꺼번에 읽는 능력과 같은 것일까요? **「You don't need long context」는 두 능력을 분리합니다.** 작업 파일과 필요한 원문은 바깥에 보관하고, 다음 행동에 필요한 정보만 짧은 문맥에 담으면 긴 작업을 이어갈 수 있는지 실험합니다. 여기서 문맥(context)은 모델이 한 번의 추론에서 받는 토큰 묶음입니다. 문맥 압축(compaction)은 그 묶음을 다음 실행에 필요한 메모로 바꾸는 과정입니다.

제목은 강하지만 결과를 “모든 모델에 긴 문맥이 필요 없다”로 읽으면 곤란합니다. 주요 폐쇄형 모델 실험에서는 짧은 문맥으로 대체로 비슷한 정확도를 유지했지만, 문서 검색에서는 정확도가 내려간 설정이 있고, 로컬 공개 가중치 모델에서는 큰 성능 붕괴도 나옵니다. 또한 비용 절감 배수 상당수는 **지금의 API 청구액이 아니라, 짧은 문맥의 서빙 이득을 가격에 반영한다고 가정한 추정치**입니다. 이 구분까지 읽어야 논문의 제안을 정확히 이해할 수 있습니다. [원문 v1](https://arxiv.org/abs/2611.05306v1)은 2026년 11월 3일 제출됐으며, 이 글은 본문 1–6절과 부록 A–G를 대상으로 합니다.

## 핵심 기여와 혁신성

이 연구가 겨냥하는 문제는 에이전트의 **전체 기록과 현재 작업 기억을 같은 공간에 계속 쌓는 관행**입니다. 과거 기록은 보존할 가치가 있지만, 그것을 매번 전부 모델에 전달하면 생성 속도와 메모리 비용이 함께 나빠집니다. 저자들은 모델의 문맥 창을 늘리는 대신, 무엇을 모델 안에 두고 무엇을 환경에서 찾아 읽을지 실험 대상으로 삼습니다.

새로운 거대 모델이나 학습 알고리즘을 평가한 논문은 아닙니다. 같은 기본 하네스에서 전체 이력 누적, 임계값 기반 압축, 매 행동 뒤 압축을 비교하고, 긴 문서는 파일로 노출하여 필요한 부분만 읽게 합니다. 그 결과를 소프트웨어 수정·터미널 작업·다중 문서 질의응답·다회 도구 사용 등으로 넓혀, **작업의 길이가 현재 문맥의 길이를 반드시 결정하지는 않는다**는 근거를 제시합니다. 모델 바깥의 실행 환경과 기억 관리가 평가의 핵심이라는 점이 학습할 부분입니다. [2–5절](https://arxiv.org/html/2611.05306v1#S2)

파급효과에 대한 저자의 제안은 자연어로 된 상태를 이어받도록 모델을 후학습하는 SSSM입니다. 다만 논문에서 실제로 학습해 비교한 SSSM 체크포인트는 없습니다. 기존 모델에 압축을 적용한 관찰과, 그 관찰에서 제안한 모델 설계를 구별해서 읽겠습니다.

## 기술적 세부사항

먼저 두 종류의 “긴 작업”을 구분해야 합니다. **Long-horizon**은 저장소 탐색→수정→테스트처럼 행동이 연속되는 작업입니다. **Long-input**은 질문은 짧아도 읽을 자료가 긴 작업입니다. 후자는 문서를 파일에 저장하고 검색·부분 읽기 도구를 주면, 여러 번 찾아 읽는 전자의 형태로 바꿀 수 있습니다. 이때 긴 원문이 사라지는 것은 아닙니다. 한 번에 모델에 넣는 분량이 줄어듭니다.

하네스(harness)는 모델 호출, 도구 실행, 관찰 반환, 제출과 종료를 연결하는 실행 틀입니다. 논문의 세 관리 방식은 이 틀에서 무엇을 다음 호출로 넘기느냐가 다릅니다.

![FHA는 모든 이력을 누적하고 EoCC는 임계값에서 실행용 메모를 만들며 SAC는 매 행동 뒤 상태를 갱신합니다.]({{ '/img/reviews/2026/short-context-compaction-review/context-regimes-ko.svg' | relative_url }})

FHA·EoCC·SAC의 정보 전달 방식. [원문 2.4.1절](https://arxiv.org/html/2611.05306v1#S2.SS4.SSS1)을 바탕으로 작성한 리뷰어 도식입니다.
{: .caption}

EoCC의 `16K / 12K`는 **전체 문맥 한도 16K 토큰, 압축 시작 임계값 12K 토큰**이라는 뜻입니다. 남은 공간은 압축문을 생성할 여유입니다. 이 한도는 작업 전체에서 쓰는 토큰의 총합과 다릅니다. 대화를 열 번 새로 만들면 각 대화는 짧아도, 열 번의 마지막 길이를 합친 총 길이는 길 수 있습니다. SAC도 행동 결과를 관찰하고 상태를 다시 쓰는 과정이 있으므로 “행동 하나만 하니 추가 추론 비용도 없다”는 뜻은 아닙니다.

평가는 과제별 정답률·성공률·재현율 등과 함께 새 입력, 캐시된 입력, 출력 토큰을 구분합니다. 비용과 관련한 핵심 식은 부록 B의 EORC(estimated optimized retail cost)입니다.

```math
\begin{aligned}
\mathrm{EORC}_M(W)
&=I C^{\mathrm{est.}}_{\mathrm{input},M}(W)\\
&\quad+H C^{\mathrm{est.}}_{\mathrm{cached},M}(W)\\
&\quad+O C^{\mathrm{est.}}_{\mathrm{output},M}(W).
\end{aligned}
```

$`M`$은 모델, $`W`$는 사용 문맥 한도입니다. $`I,H,O`$는 각각 백만 토큰 단위의 비캐시 입력·캐시 입력·출력 총량입니다. $`C`$는 해당 토큰 종류의 백만 토큰당 추정 달러 가격이므로, 곱해서 더하면 실험 묶음의 달러 비용이 됩니다. 압축으로 늘어난 토큰도 총량에 반영되지만 **단가 자체를 문맥에 따라 낮추는 가정**이 들어갑니다. 식의 구성과 실제 API 가격과의 차이는 부록 B 리뷰에서 다시 확인합니다. [원문 식 (4)](https://arxiv.org/html/2611.05306v1#A2)

## 챕터별 상세 리뷰

### 📖 **Chapter 1: Introduction**

첫 장은 성능보다 먼저 문맥의 물리적 비용을 짚습니다. 일반적인 attention 기반 모델에서는 현재 토큰이 참고할 문맥이 길어질수록 생성 단계의 계산과 KV 캐시 부담이 커집니다. KV 캐시는 이전 토큰에서 계산한 key·value를 재사용하는 메모리입니다. Figure 1은 이미 입력 KV 캐시가 있는 조건에서 출력 100만 토큰을 생성하는 GPU 비용을 비교합니다.

| --- | ---: |
| GLM 5.2 | 3.6배 |
| Kimi K2.6 | 5.6배 |
| Qwen 3 Coder Next | 7.0배 |

같은 GPU 수에서 측정한 최고 지속 decode 처리량을 H100 한 대당 시간당 3.85달러라는 2026년 9월 Nebius 가격으로 환산한 결과입니다. 따라서 **출력 토큰 생성 구간의 하드웨어 효율**에 관한 수치이며, 압축·검색·입력 처리까지 포함한 서비스 전체 지연이 7배 줄었다는 결과가 아닙니다. Figure 2는 별도로 DGX Spark에서 단일 요청을 처리할 때 문맥이 길어지면 일부 모델의 토큰 간 지연이 약 두 배가 되고 메모리도 늘어나는 모습을 보여 줍니다. 클라우드 다중 요청 처리량과 로컬 단일 요청 지연은 다른 측정입니다. [Figure 1–2](https://arxiv.org/html/2611.05306v1#S1.F1)

이어 Table 1은 영문 문학 작품의 길이와 모델 문맥 창을 나란히 놓습니다. 단어를 토큰으로 바꿀 때 약 1.33토큰/영단어를 사용하는 직관용 비교이며, 토크나이저와 문서에 무관한 법칙은 아닙니다. 저자들은 큰 문맥을 지원하는 능력과 작은 문맥에서 효율적으로 작동하는 능력이 별개임을 문제 삼습니다.

이후 논리는 순서대로 진행됩니다. 작업 도중 이력이 쌓이는 LCW1(long-horizon)과 처음부터 자료가 긴 LCW2(long-input)를 구별하고, LCW2도 선택적 읽기를 통해 LCW1로 바꿀 수 있다고 봅니다. 여기서 RQ1은 긴 작업을 짧은 문맥으로 끝낼 수 있는지, RQ2는 긴 입력도 가능한지, RQ3는 대화당 환경 행동을 하나로 제한해도 가능한지를 묻습니다. 이 구분이 다음 장의 실험 설계를 결정합니다.

### 📖 **Chapter 2: Methodology**

이 장은 “짧다”와 “긴 작업”의 의미를 고정하고, 비교 대상과 측정 조건을 순서대로 정합니다.

#### 2.1 Definitions

추론 단계(inference step)는 모델을 한 번 호출해 출력을 얻는 단위입니다. 입력 문맥에는 시스템 지침, 과제, 이전 출력과 도구 결과가 들어갈 수 있고, 출력 문맥에는 추론 과정·도구 호출·사용자 응답 등이 들어갑니다. 논문은 문맥이라는 단어를 입력만, 입력과 출력의 결합, 또는 출력 여유까지 포함하는 공간이라는 의미로도 사용한다고 명시합니다. 따라서 개별 표에서 어떤 길이를 측정하는지 확인해야 합니다.

문맥 창(context window)은 한 번에 다룰 수 있는 토큰 공간이고, 문맥 창 크기는 모델이나 서빙 설정이 허용하는 한도입니다. 저자들이 말하는 긴 문맥은 당시 frontier 모델의 약 256K 이상 규모를 향해 자라는 실행 방식까지 포함합니다. 실제 실행 하나가 그 한도에 도달해야만 긴 문맥 방식으로 분류되는 것은 아닙니다. 짧은 문맥은 대체로 16K–50K를 뜻합니다. 이는 상대적으로 짧다는 뜻이며, 일상 언어 기준으로 아주 작은 메모라는 뜻은 아닙니다.

그다음 긴 입력은 **이용 가능한 원자료의 크기**, 긴 작업은 **순차 행동과 의존 관계의 길이**로 정의합니다. 이 정의 덕분에 문서를 여러 번 부분적으로 읽는 실행을 “긴 입력을 쓰지 않은 실험”으로 오해하지 않게 됩니다. 원자료는 여전히 깁니다. 모델이 한꺼번에 읽지 않을 뿐입니다. [2.1절](https://arxiv.org/html/2611.05306v1#S2.SS1)

#### 2.2 Benchmarks

긴 작업 그룹은 다음 여섯 벤치마크입니다. 소프트웨어 수정뿐 아니라 사용자와의 대화, 정보 검색, 상태가 바뀌는 도구 호출도 포함합니다.

| τ²-bench | 소매·항공·통신 golden set 184개, 사용자 요청과 최종 환경 상태를 함께 평가 |
| BFCLv3 | 긴 문맥 다회 도구 사용 에피소드 200개 |

긴 입력 그룹은 현실적인 문서 질의응답 세 종류와 진단 과제 네 종류입니다. LongBench v2는 8K–약 2M **단어** 범위의 입력을 갖는 503개 객관식 질문입니다. LOONG은 영문·중문 금융 보고서, 법률 사건, 논문 등을 이용하는 다중 문서 질문 1,600개입니다. AA-LCR은 평균 약 100K **토큰**의 실제 문서 묶음을 읽는 질문 100개입니다. 단어와 토큰을 같은 단위로 읽지 않아야 합니다.

진단 과제는 NIAH의 125개 삽입 위치·길이 조합(16K–약 500K 토큰), RULER의 13개 유형(256K·500K 토큰), Counting-Stars의 192개 질문(4K–128K 토큰), BABILong의 10개 유형·5개 길이(64K–1M 토큰), 총 550개 질문입니다. 단순 키워드 하나 찾기만 있는 것은 아닙니다. 수정된 수치를 구별하거나 여러 사실을 연결하고, 답의 집합을 추적하는 과제도 포함됩니다. 이후 결과에서 정답률, 재현율, 완전 일치가 달리 쓰이는 이유입니다. [2.2절](https://arxiv.org/html/2611.05306v1#S2.SS2)

#### 2.3 Models

주요 정확도 실험의 작업 모델은 Claude Opus 4.5와 GPT 5.6 Sol입니다. 두 계열을 비교하여 한 제공사의 모델에만 압축이 잘 맞는 현상인지 살펴봅니다. Figure 1·4의 클라우드 처리량 실험은 별도 모델인 GLM 5.2, Kimi K2.6, Qwen 3 Coder Next로 수행합니다. 이 공개 모델의 처리량 변화에서 얻은 비용 비율을 폐쇄형 모델의 가상 최적화 가격에 적용한다는 점을 기억해야 합니다.

로컬 실험은 통합 메모리 128GB 중 약 109GB를 모델 서빙에 이용할 수 있는 DGX Spark에서 수행합니다. Qwen 3.6 27B와 Qwen 3 Coder Next는 NVFP4로, Gemma 4 31B는 GGUF Q4_K_M, Step 3.7 Flash는 Q3_K_M, MiniMax M2.7은 IQ3_XXS로 서빙합니다. 양자화는 가중치 등의 수치 정밀도를 줄여 메모리 사용량을 낮추는 방식입니다. 여기서는 같은 이름의 비양자화 모델과 동일한 결과를 보장하지 않습니다.

모델 구조도 다양합니다. Qwen 계열은 Gated DeltaNet과 full attention을 섞고, Gemma와 Step은 국소 창 attention과 global/full attention을 섞습니다. MiniMax는 full-softmax grouped-query attention을 사용합니다. 원문은 이 다양성을 짧은 문맥 실험의 배경으로 들지만, 구조별 원인 분석을 따로 증명한 것은 아닙니다. 로컬 성능의 차이는 부록 D에서 다시 확인합니다. [2.3절](https://arxiv.org/html/2611.05306v1#S2.SS3)

#### 2.4 Harnesses

두 기본 하네스는 모두 ReAct 방식입니다. 모델이 행동을 선택하고, Bash 실행 결과를 관찰한 뒤, 다음 행동을 정합니다. mini-swe-agent는 저장소나 컨테이너에서 수정하고 패치를 제출합니다. mini-agent는 그 반복 구조를 유지하면서 과제 지침·도구·제출 규칙을 다른 벤치마크에 맞게 바꿉니다. 원문을 별도 학습한 모델과 비교하는 실험이 아니라, 실행 틀의 문맥 관리 방식을 바꾸는 실험입니다.

**2.4.1 Accommodations for long conversational context.** FHA(Full-History Accumulation)는 모든 행동과 관찰을 한 대화에 누적합니다. EoCC(End-of-Conversation Compaction)는 임계값에 도달하면 현재 대화 안에서 압축 메모를 생성하고, 원래 과제와 메모를 넣은 새 대화를 시작합니다. 압축을 완료하지 못하고 총 한도에 이르면 종료될 수 있으므로, 총 한도와 임계값은 별도로 둡니다.

SAC(Single-Action Compaction)는 과제와 현재 의미 상태를 받아 환경 행동을 정확히 한 번 하고, 결과를 관찰한 뒤 상태를 갱신합니다. 그 대화를 버리고 새 대화에서 다음 행동을 합니다. 여기서 의미 상태(semantic state)는 다음 실행이 이어받을 수 있도록 자연어로 표현한 작업 상태입니다. 원문 Figure 3의 오른쪽 패널은 행동을 한 대화 안에 압축 요청과 상태 갱신을 덧붙인 뒤 새 대화로 넘어가는 과정을 보여 줍니다.

길이 지표도 두 가지입니다. Total length는 각 하위 대화의 마지막 길이를 모두 더한 값이고, peak length는 가장 긴 단일 대화의 길이입니다. 짧은 peak는 필요한 문맥 창이 작다는 뜻입니다. total까지 줄었다는 뜻은 아니며, 둘을 구별해야 압축 비용을 놓치지 않습니다.

**2.4.2 Accommodations for long inputs.** 긴 입력을 `input01.txt`, `input02.txt` 같은 파일로 두고, 초기 대화에는 파일 정보와 과제를 제공합니다. 모델은 `sed`, `awk`, `head` 등으로 필요한 부분을 읽습니다. 검색 도구가 파일 전체를 훑더라도 모델 문맥에는 반환된 발췌만 들어갑니다. 긴 자료의 저장·검색과 모델의 직접 독해가 분리되는 구조입니다. [2.4절](https://arxiv.org/html/2611.05306v1#S2.SS4)

#### 2.5 Latency and throughput measurement

클라우드에서는 최대 실험 문맥과 체크포인트를 함께 담을 수 있는 H100 배치를 고정합니다. Qwen에는 8개, GLM과 Kimi에는 16개 GPU를 사용합니다. 가장 긴 공통 접두사를 한 번 prefill하고 prefix caching을 켠 뒤, 중첩 접두사에서 길이를 균등하게 뽑은 요청마다 정확히 1,024토큰을 생성합니다. 동시 요청 수를 바꿔 KV 캐시 preemption 없이 가장 높은 지속 처리량을 보고합니다. 반복 측정 변동은 최대 2%였다고 명시합니다.

로컬에서는 모델 하나·요청 하나로 문맥 접두사 길이를 바꾸고, 이어지는 1,024토큰의 평균 토큰 간 지연과 기기 메모리를 측정합니다. 처리량은 평균 지연의 역수입니다. 클라우드 측정은 포화 부하에서의 처리량, 로컬 측정은 배치 크기 1의 생성 속도이므로 서로 바꿔 읽을 수 없습니다. 이 장은 다음 장부터 나타나는 정확도 비교와 시스템 효율 비교의 조건을 분리해 줍니다. [2.5절·Figure 4](https://arxiv.org/html/2611.05306v1#S2.SS5)

### 📖 **Chapter 3: Long-horizon tasks don’t need long contexts**

여섯 긴 작업 벤치마크에서 EoCC와 FHA를 비교합니다. SWE-bench 두 종류, Terminal-Bench, FRAMES에서는 `48K/36K`, `32K/24K`, `24K/18K`, `16K/12K`를 사용합니다. BFCLv3는 `24K/18K`부터 `12K/8K`, τ²-bench는 `16K/12K`부터 `8K/6K`까지 실험합니다. 이렇게 모델당 22개 임계값 설정을 비교합니다.

Figure 5의 위쪽은 기준선 대비 **정확도의 퍼센트포인트 차이**입니다. Opus는 −3.7~+5.6p.p., GPT는 −3.3~+4.4p.p. 범위입니다. 어느 모델에서도 22개 중 2p.p. 넘게 하락한 설정은 최대 5개입니다. 이는 대부분의 설정에서 기준선에 가깝다는 근거이지, 모든 설정의 성능 보존이나 통계적 동등성을 증명하는 결과는 아닙니다.

아래쪽의 비용 절감은 Opus 2.2–8.8배, GPT 2.4–5.0배로 보고되지만 부록 B의 **추정 최적화 가격** 기준입니다. 저자들은 압축 후 같은 일을 다시 하느라 전체 토큰량이 크게 늘면 이 이점이 줄어들 수 있다고 논의합니다. 전반적으로 그런 문제가 지배적이지 않았다고 설명하면서도, 상세 표에는 총 길이가 늘어난 설정이 남아 있습니다. 이 장의 공헌은 최대 문맥 창을 줄여도 주요 폐쇄형 모델의 작업 성공률이 대체로 유지된다는 관찰이며, 개별 비용·실패 차이는 부록 C로 이어집니다. [3절·Figure 5](https://arxiv.org/html/2611.05306v1#S3)

#### 3.1 Long-horizon tasks may sometimes need the history

저자들은 압축이 손실성임을 명시합니다. 정해진 메모 크기에 동전 던지기 결과를 계속 압축하면 언젠가 일부 순서를 잃습니다. 나중에 “i번째 결과”를 물으면 그 누락이 실패를 일으킬 수 있습니다. 이미 압축한 내용을 다시 압축하면 손실이 누적될 수도 있습니다.

제시하는 대응은 **이력을 없애지 말고 외부에 보존한 뒤 선택적으로 읽게 하는 것**입니다. “과거를 볼 필요가 없다”와 “과거 전부를 항상 현재 문맥에 넣을 필요는 없다”는 다른 주장입니다. 이 절은 후자를 말하며, 이력 조회를 다음 장의 긴 입력 문제로 연결합니다. [3.1절](https://arxiv.org/html/2611.05306v1#S3.SS1)

### 📖 **Chapter 4: Long-input tasks don’t need long contexts**

일곱 긴 입력 벤치마크에서는 전체 원문을 대화에 붙이는 기준선과, 파일에서 선택적으로 읽고 필요하면 압축하는 실행을 비교합니다. 따라서 이 장의 차이는 **압축 하나만의 효과가 아니라 입력 접근 방식까지 바꾼 효과**입니다.

Figure 6의 정확도 차이는 Opus −0.4~+40.0p.p., GPT +1.0~+30.9p.p.입니다. 가장 큰 개선을 모든 문서 과제의 일반적인 향상률로 읽어서는 안 됩니다. 실제로 LongBench v2의 Opus는 68.0%에서 67.6%로 약간 내려가며, 검색으로 표적을 직접 찾기 쉬운 NIAH에서는 60.0%에서 100.0%로 크게 오릅니다. 과제별 수치는 부록 F에서 나눠 보겠습니다.

추정 최적화 비용 절감은 Opus 6.5–54.6배, GPT 4.4–233.3배입니다. 여기에는 선택적 읽기로 입력 자체를 덜 넣은 효과와 짧은 문맥의 가상 단가 효과가 모두 들어갑니다. 이 숫자를 “압축 버튼만 눌렀을 때 API 비용”으로 제시하면 실험 조건이 달라집니다.

Figure 7은 Opus의 LongBench v2 `16K/12K`, Figure 8은 LOONG `48K/40K` 실행을 그립니다. 가로축은 문서 길이의 로그 척도, 세로축은 하위 대화들을 합친 총 길이의 선형 척도입니다. 문서가 길어져도 총 대화 길이가 대체로 비슷한 띠에 머물고 일부 긴 이상치가 있습니다. 이는 읽을 원자료가 커졌다고 모델이 매번 비례해서 많이 읽은 것은 아니라는 관찰입니다. 모든 자료를 빠짐없이 읽었다는 의미도, 모든 과제의 읽기량이 상수라는 증명도 아닙니다.

여러 벤치마크에서 압축 횟수 중앙값이 0에 가깝다는 결과는 특히 중요합니다. 이 경우 주된 문맥 절약은 압축이 아니라 선택적 읽기에서 나옵니다. 이 장은 긴 입력의 크기만으로 긴 문맥의 필요성이 입증되지는 않는다고 결론짓고, 다음 장은 행동 사이에 남기는 정보까지 더 줄여 봅니다. [4절·Figures 6–8](https://arxiv.org/html/2611.05306v1#S4)

### 📖 **Chapter 5: Compaction can be performed after every action**

SAC는 훨씬 강한 실험입니다. 매번 과제와 상태를 받되 환경 행동은 하나만 한 뒤 대화를 새로 만듭니다. 적용 범위는 mini-swe-agent를 이용한 SWE-bench Verified와 Terminal-Bench 두 가지이며, 이 결과를 모든 일곱 긴 입력 벤치마크의 SAC 검증으로 확장할 수는 없습니다.

| 모델·과제 | FHA 정확도 | SAC 정확도 | FHA peak 중앙값/최대 | SAC peak 중앙값/최대 |
| --- | ---: | ---: | ---: | ---: |
| Opus · SWE-bench Verified | 70.0% | 70.2% | 32K / 200K | 8K / 16K |
| Opus · Terminal-Bench 2.1 | 47.2% | 51.8% | 27K / 130K | 9K / 19K |
| GPT · SWE-bench Verified | 84.4% | 82.4% | 18K / 173K | 7K / 15K |
| GPT · Terminal-Bench 2.1 | 87.6% | 84.3% | 17K / 133K | 8K / 37K |

원문 Table 2를 필요한 열만 옮겼습니다. 정확도는 과제 성공 비율, peak는 과제별 가장 큰 단일 문맥의 중앙값/최대값이며 단위는 천 토큰입니다. GPT의 Terminal-Bench SAC는 89개 중 75개 성공에 해당합니다. Opus는 기준선 수준을 유지하거나 개선했지만 GPT는 각각 2.0·3.3p.p. 내려갑니다. 따라서 저자의 주장은 “극단적인 압축에도 성능이 파국적으로 무너지지 않았다”에 가깝습니다. 표에는 SAC의 전체 지연이나 전체 비용 비교가 없으므로 peak 감소율을 곧바로 서비스 비용 감소율로 바꿀 수 없습니다. [5절·Table 2](https://arxiv.org/html/2611.05306v1#S5.T2.fig1)

#### 5.1 Semantic State Space Models (SSSMs)

저자들은 이 관찰에서 SSSM이라는 후학습 방향을 제안합니다. 모델이 ① 자연어 상태를 이해하고 ② 다음 행동을 판단하며 ③ 행동하고 ④ 결과를 관찰한 뒤 ⑤ 다음 추론 인스턴스가 이어받을 수 있게 상태를 다시 쓰도록 학습하자는 것입니다. 기존 State-Space Model이 토큰 사이에 신경망 내부 상태를 유지한다면, 여기서는 대화 턴 사이에 사람이 읽을 수 있는 자연어 상태를 유지합니다. 이름이 비슷해도 같은 구조는 아닙니다.

아래는 Figure 3과 5.1절을 설명하기 위해 다시 쓴 **의사코드**입니다. 원문 구현 코드나 실행 결과가 아닙니다. 입력, 환경 관찰, 상태 갱신, 다음 행동의 연결을 드러내는 데 목적이 있습니다.

```text
입력: 과제, 현재 의미 상태, 계속 유지되는 파일·도구 환경
반복:
    새 대화에 시스템 지침 + 과제 + 현재 의미 상태를 제공
    모델이 다음 환경 행동 하나를 선택
    환경이 행동을 실행하고 관찰 결과를 반환
    모델이 관찰을 반영하여 다음 실행용 상태를 작성
    완료 조건을 충족하면 정해진 결과를 제출하고 종료
    아니면 갱신된 상태를 넘기고 현재 대화를 종료
출력: 제출 결과와 환경에 남은 산출물
```

토큰 효율이 좋아질 수 있다는 주장은 앞의 서빙 실험에 근거합니다. 반면 이전 문맥의 적절한 부분을 찾도록 학습할 부담이 줄어 데이터 효율도 좋아질 것이라는 설명은 **저자의 추측**입니다. 실제 SSSM 학습 실험의 결과는 아닙니다. 이 절은 관찰에서 모델 설계 제안으로 넘어가는 지점이며, 다음 결론에서 그 범위를 정리합니다. [5.1절](https://arxiv.org/html/2611.05306v1#S5.SS1)

### 📖 **Chapter 6: Conclusion**

저자들은 RQ1–RQ3에 긍정적으로 답합니다. 긴 작업에서는 압축이 대체로 성공률을 보존하고, 긴 입력에서는 선택적 읽기가 문맥을 짧게 하며, 행동마다 상태를 갱신해도 주요 실험의 성능이 크게 무너지지 않았다는 결론입니다. 계산 가능성에 관한 직관도 덧붙이지만, 실험 결과가 모든 가능한 작업의 짧은 문맥 해결 가능성을 수학적으로 증명한 것은 아닙니다.

실제로 결론은 **긴 문맥이 유익한 과제의 존재를 배제하지 않으며, 모든 과제를 짧은 문맥으로 풀 수 있다고 증명하지도 않았다**고 명시합니다. 실험한 설정들에서는 긴 입력과 긴 행동 이력이라는 이유만으로 큰 작업 문맥이 반드시 필요하다고 보기는 어렵다는 주장입니다. 이후 부록은 그 결론을 지탱하는 압축 지침, 비용 가정, 상세 결과를 차례로 제시합니다. [6절](https://arxiv.org/html/2611.05306v1#S6)

### 📖 **Chapter Appendix A: What characterizes a good compaction?**

이 부록은 압축을 일반적인 요약과 구별합니다. 사람이 중간에 방향을 바꾸는 코딩 작업에서는 이후 피드백을 처리하는 데 필요한 선호나 지침도 남겨야 합니다. 반면 여기서 주로 찾으려는 것은 자율적으로 주어진 과제를 마치는 데 유용하고 저렴한 압축입니다. 그 사용 맥락이 완전히 같지는 않습니다.

저자들은 압축 방법과 압축할 정보 범위를 바꿔 살펴봤다고 설명합니다. 단순 요약은 실행 기록의 모든 사실에 고르게 무게를 주거나, 자주 반복된 내용에 과도하게 비중을 줄 수 있습니다. 그러나 다음 실행에 중요한 것은 “무슨 일이 있었는가”를 아름답게 서술하는 것이 아니라 **앞으로 무엇을 해야 하는가를 정확히 이어주는 것**입니다.

원문이 좋다고 설명하는 구성은 입력 과제의 원문 또는 거의 그대로인 복사, 현재 하고 있는 일과 의도·다음 단계, 향후 실행에 직접 필요한 산출물입니다. 여기에는 세분화한 계획, 완료 판단 조건, 관련 정보 자체나 그것을 다시 읽을 수 있는 위치가 포함됩니다. 예를 들어 파일의 내용을 전부 기억하기보다 정확한 경로와 확인 결과를 남기는 방식입니다. 이는 리뷰어가 새로 제안하는 실험이 아니라 부록의 압축 설계 원칙입니다. 별도의 방법별 정량 비교표가 제공되지는 않으므로 압축 구조의 우수성을 수치 순위로 단정하지 않습니다. 다음 부록은 이 실행이 얼마나 저렴해지는지를 계산하는 가정을 설명합니다. ### 📖 **Chapter Appendix B: Estimated optimized retail cost**

비용을 읽을 때 가장 중요한 부록입니다. 먼저 동일 GPU 배치에서 문맥 16K와 256K의 처리량 비율을 측정합니다. GPU 수와 시간당 가격이 고정되어 있으므로 출력 토큰당 비용 비율은 처리량 비율의 역수입니다.

```math
\begin{aligned}
r_M&=\frac{C_{\mathrm{output},M}(16\mathrm{K})}{C_{\mathrm{output},M}(256\mathrm{K})}\\
&=\frac{T_M(256\mathrm{K})}{T_M(16\mathrm{K})}.
\end{aligned}
```

원문 식 (1)입니다. $`T_M(W)`$는 이미 KV 캐시가 있는 입력 뒤에서 측정한 초당 출력 토큰 처리량입니다. 측정된 비율은 GLM 0.2772, Kimi 0.1777, Qwen 0.1439입니다. 저자들은 이 평균을 반올림한 $`r=0.20`$을 이후 추정에 사용합니다. 특정 폐쇄형 모델에서 0.20을 직접 측정한 것은 아닙니다.

다음으로 최대 기준 문맥의 출력 가격을 Opus 25달러, GPT 20달러/백만 출력 토큰에 고정합니다. 기준 문맥 $`W^{\mathrm{max}}_M`$은 Opus 200,000토큰, GPT 272K토큰입니다. GPT가 지원하는 최대 문맥 1,050,000토큰과 이 기준값을 혼동하면 안 됩니다. 272K는 논문이 채택한 표준 가격 구간의 상한입니다. 이후 16K까지 선형으로 단가를 내리고, 더 작은 문맥에서는 더 내리지 않습니다.

```math
\begin{aligned}
f_M(W)&=r+(1-r)\\
&\quad\cdot\frac{\max(W,16\mathrm{K})-16\mathrm{K}}
{W^{\mathrm{max}}_M-16\mathrm{K}},\\[3pt]
C^{\mathrm{est.}}_{\mathrm{output},M}(W)
&=C_{\mathrm{output},M}(W^{\mathrm{max}}_M)f_M(W).
\end{aligned}
```

원문 식 (2)의 대괄호를 설명용 계수 $`f_M(W)`$로 나누어 쓴 동치식입니다. 이 계수가 원래 출력 가격에 곱해집니다. 기준 문맥에서는 1, 16K 이하에서는 0.20이 됩니다. 새 입력 가격은 이 출력 가격의 1/5, 캐시 입력 가격은 다시 새 입력의 1/10로 둡니다. 이것이 식 (3)이며, 이 가격들을 앞서 본 식 (4)에 넣어 토큰 종류별 비용을 합산합니다. **공개 모델에서 측정한 시스템 이득을 폐쇄형 API에도 가격으로 전달한다고 가정한 모형**입니다.

반면 nominal retail cost는 실제 공개된 표준 API 가격을 토큰 총량에 적용한 값입니다. 논문의 기준일인 2026년 9월 29일 가격은 새 입력/캐시 입력/출력 백만 토큰당 Opus 5/0.50/25달러, GPT 4/0.40/20달러입니다. 이 둘을 나란히 보면 압축 때문에 늘어난 입력과 출력의 영향을 분리할 수 있습니다. 다음 부록의 모든 절감 배수는 어느 열을 비교했는지 확인해야 합니다. [Appendix B, 식 (1)–(4)](https://arxiv.org/html/2611.05306v1#A2)

### 📖 **Chapter Appendix E: Selective reading of long inputs**

mini-agent는 긴 문서를 파일로 노출하고 모델이 질문의 대상·수치·주장을 검색하게 합니다. 검색은 파일 전체를 훑을 수 있지만, 대화에 들어오는 것은 반환된 발췌뿐입니다. `doc-stats`는 크기, `docs-list`는 목록, `doc-read`는 제한된 읽기, `doc-syn`은 검색어 변형을 돕습니다.

#### E.1 Instructions supplied to the agent

`doc-read`는 기본 6,000자, 최대 8,000자의 창을 읽고 다음 연속 구간을 읽을 명령도 알려 줍니다. 줄 범위나 문자 위치로 요청할 수 있습니다. 지침은 문서를 통째로 출력하지 말고 질문의 선택지가 의존하는 대상과 주장을 찾은 다음 주변 문맥을 확인하도록 명시합니다. 이 제한된 읽기 인터페이스도 실험 조건의 일부입니다.

#### E.2 Examples from recorded runs

원문의 세 사례는 전체 읽기 비용의 전형적인 추정치가 아니라 **실행 원리를 보여 주는 발췌**입니다. 첫 사례는 약 100만 자·1만 9천 줄의 Kalamang 문법에서 단어를 찾아 문법 문맥을 읽습니다. 두 번째는 약 13만 8천 자의 논문 묶음에서 `OpenMoE`를 검색한 뒤, 해당 파일 시작 부분 1,000자만 읽어 논문 정체성을 확인합니다. 세 번째는 약 40만 4천 자의 네 문서에서 broadcasting 제외 조건이 걸린 산업별 수치를 찾아, 수치와 기간을 주변 문장으로 확인합니다.

여기서 중요한 결정은 단어를 찾은 즉시 답하지 않고, 근처 문법과 예시를 추가로 읽는 것입니다. 두 번째 사례도 키워드 발견 뒤 제목을 확인하고, 세 번째도 숫자뿐 아니라 산업과 기간을 확인합니다. 이 부록의 기여는 선택적 읽기가 단순 문자열 복사와 다르다는 점을 실제 흔적으로 보여 주는 것입니다. 이어지는 부록 F는 같은 방식의 평가 수치를 제시합니다. [Appendix E](https://arxiv.org/html/2611.05306v1#A5)

Table 11–17은 긴 입력 전체를 붙인 기준선과 선택적 읽기·필요시 압축을 비교합니다. 토큰은 벤치마크 전체 백만 토큰이며, 압축 횟수는 과제별 평균/중앙값/최대값입니다. 정확도 열 이름이 과제마다 다르므로 하나의 성공률로 합치지 않겠습니다.

**Table 11, LongBench v2.** `16K/12K`에서 Opus는 68.0→67.6%, GPT는 70.8→72.6%입니다. 압축 횟수는 각각 1.4/1/9와 0.1/0/3입니다. GPT의 명목 비용은 79.20→90.20달러로 늘고 추정 최적화 비용은 18.04달러입니다. 긴 입력에서도 명목 가격과 가상 최적화 가격의 차이가 나타납니다.

**Table 12, LOONG.** 평균 점수/완전 정답률을 함께 보고합니다. 모든 설정에서 두 지표 모두 기준선보다 높습니다. Opus의 기준선 70.1/38.9%는 `32K/24K`에서 80.2/53.7%, GPT의 기준선 79.3/44.4%는 `48K/40K`에서 84.6/53.0%입니다. 큰 두 설정에서는 두 모델의 압축 중앙값이 0입니다. 다만 `16K/12K`의 최대 압축 횟수는 Opus 46회, GPT 61회이므로 중앙값이 작다고 모든 실행이 짧고 간단했다고 볼 수는 없습니다.

**Table 13, AA-LCR.** `16K/12K`에서 Opus는 65.0→84.0%, GPT는 82.0→83.0%입니다. 문서에 흩어진 정보를 모아 추론하는 현실적 과제에서도 선택적 읽기가 유용했던 사례입니다. 여기서도 최대 개선을 모든 모델에 동일하게 적용하지 않고 두 기준선을 분리해 봐야 합니다.

**Table 14, NIAH.** Opus는 60.0→100.0%, GPT는 80.0→100.0%입니다. 두 모델 모두 압축이 한 번도 없었습니다. 저자들은 질문과 표적 문장 또는 알려진 동의어 사이의 비교적 직접적인 어휘 겹침으로 표적을 찾기 쉬웠다고 설명합니다. 따라서 이 사례의 개선은 손실 압축의 우수성보다 검색 접근 방식의 효과를 보여 줍니다.

**Table 15, RULER.** 평균 재현율/완전 일치율은 Opus 62.5/51.3→95.7/94.4%, GPT 65.5/54.9→96.4/95.4%입니다. 재현율은 요구된 답 집합을 얼마나 회수했는지, 완전 일치는 답 전체를 맞혔는지 보는 지표입니다. 압축 중앙값은 둘 다 0입니다. 평균 압축 횟수 표시는 반올림해 0.0이지만 최대는 7회와 2회이므로, 이 표를 “단 한 번도 압축하지 않았다”로 읽으면 틀립니다.

**Table 16, Counting-Stars.** 두 모델의 선택적 읽기 평균 점수는 99.7%, 완전 일치율은 81.2%입니다. 기준선 완전 일치율은 Opus 65.1%, GPT 76.6%였습니다. 여기서는 정말로 압축을 전혀 하지 않았습니다. 거의 모든 숫자를 회수하는 것과 모든 숫자를 한꺼번에 정확히 맞히는 것의 차이가 평균과 완전 일치의 간격에 드러납니다.

**Table 17, BABILong.** Opus 67.1→92.0%, GPT 70.7→94.0%입니다. 16K 한도를 사용하며 GPT는 압축 0회, Opus는 과제당 최대 1회입니다. 이 부록은 일곱 과제에서 선택적 읽기의 효과를 보여 주지만, 그 효과를 압축 횟수와 분리해 읽어야 한다는 점도 함께 보여 줍니다. 마지막 부록은 이 모든 실행을 연결한 프롬프트의 구체적인 구성입니다. [Appendix F, Tables 11–17](https://arxiv.org/html/2611.05306v1#A6)

### 📖 **Chapter Appendix G: Agent outlines**

#### G.1 mini-swe-agent

사용한 기본 하네스는 mini-swe-agent v2.4입니다. 환경 연결과 문맥 관리에 필요한 작은 변경을 제외하고 과제를 푸는 기본 반복은 유지했다고 설명합니다. 압축 프롬프트는 작업과 도구 호출을 멈추고, 다음 대화에 넘길 짧은 인계 메모만 작성하도록 합니다.

남겨야 할 내용은 목표, 확인된 사실, 이미 적용한 변경, 검증, 실패한 시도, 남은 계획 순서입니다. 경로·심볼·명령·관찰값·오류를 정확히 남기고, 검증된 사실과 미확인 생각을 구별합니다. 출력이 잘렸다면 다시 필요한 범위만 읽을 명령을 적습니다. 이는 “전체 대화 요약”보다 실행 가능한 인계문에 가까운 형식입니다.

#### G.2 mini-agent

일반화한 하네스는 시스템 프롬프트에서 증거 확인→행동→관찰→검증을 지시하고, 사용자 프롬프트에서 과제·입력 정보·도구·작업 절차·제출 형식·이전 인계문을 제공합니다. 압축 프롬프트는 현재 진행과 최선의 답, 정확한 근거 위치, 해결·미해결·실패 사항, 다음 행동과 완료 조건을 남깁니다.

마지막 변수 표는 `task`, `input_details`, `tools`, `work_instructions`, `command_rules`, `submission_instructions`, `context_instructions`, `recap_section`, `recap`, `persistence`, `handoff_details`, `submission_reminder`의 역할을 구분합니다. 특히 `persistence`는 대화가 바뀌어도 남는 파일·환경과 메모에 보존해야 하는 정보를 구분합니다. `submission_reminder`는 완료 직전 검사와 제출 규칙을 잊지 않게 합니다. 프롬프트 틀을 공개했다는 사실과 이 글에서 실제 벤치마크를 재실행해 재현했다는 주장은 별개입니다. 이 리뷰는 원문과 그 예시를 분석했으며 실험 코드를 실행하지 않았습니다. ## 실험 결과 심층 분석

이 논문의 결과는 세 층으로 나누면 명확해집니다. 첫째, **같은 기본 에이전트의 이력을 압축하는 비교**에서는 주요 폐쇄형 모델의 정확도가 대체로 유지됩니다. 둘째, **전체 문서 입력을 도구를 통한 선택적 읽기로 바꾸는 비교**에서는 검색 절차와 문맥 관리가 함께 달라집니다. 셋째, **서빙 효율 측정**은 이미 캐시된 입력 뒤의 출력 생성 처리량 또는 로컬 토큰 간 지연을 측정합니다. 세 결과를 합쳐 “어떤 모델이든 압축하면 정확도 손실 없이 API 비용이 수십 배 줄어든다”고 말할 수는 없습니다.

특히 실용적 판단에는 세 가지 수치가 함께 필요합니다. FRAMES는 모든 압축 설정에서 두 모델 모두 기준선보다 낮습니다. 공개 가중치 Qwen Coder는 가장 작은 SWE 설정에서 53.0%에서 3.6%로 무너집니다. SAC에서 GPT의 성공률은 두 코딩 과제 모두 내려갑니다. 이 예외들은 원문의 결론을 부정하기보다 **모델·과제·한도·압축 방식이라는 조건을 생략하지 말아야 한다는 근거**입니다.

비용에서도 명목 비용과 EORC를 같이 봐야 합니다. 압축은 추가 상태 작성과 입력 재전달을 일으킬 수 있고, 실제 표에서 출력량과 새 입력량이 증가합니다. SWE GPT의 16K 설정처럼 명목 API 가격으로는 비싸지는 경우가 있습니다. 반면 LOONG처럼 긴 입력 자체를 덜 전달하여 명목 비용도 크게 줄어드는 경우가 있습니다. 두 절감 원인은 동일하지 않습니다.

통계적 신뢰도에도 경계가 있습니다. 논문은 클라우드 처리량 반복 측정 변동이 최대 2%라고 보고하지만, 주요 과제 정확도 표에 대한 신뢰구간·유의성 검정·반복 실행 분산은 보고하지 않습니다. 따라서 0.2p.p. 또는 1.0p.p. 차이를 통계적으로 확정된 우열로 표현하지 않았습니다. 또한 Table 2의 Best EoCC는 평가한 설정 중 가장 높은 정확도이며, 모든 과제에 사전 고정한 단일 운영 설정의 성능은 아닙니다. ## 기술적 함의와 응용

저자가 제시한 방향은 **큰 문맥 창에 모든 기억을 모으는 모델에서, 짧은 실행 상태를 이어받는 모델로의 이동**입니다. SSSM은 그 제안의 이름이며, 데이터 효율이나 기존 전체 이력 모델과의 동등한 성능은 아직 이 논문에서 검증한 결과가 아닙니다. 실제로 확인한 것은 기존 모델에 상태 압축과 선택적 읽기를 적용했을 때의 벤치마크 결과입니다.

리뷰어 관점에서 가장 유용한 설계 구분은 저장과 작업 기억의 분리입니다. 동전 던지기 이력처럼 손실 없이 보존해야 하는 정보는 외부 기록에 남기고, 현재 문맥에는 다음 행동에 필요한 상태와 다시 읽을 위치를 둡니다. 부록 A·G의 완료 조건, 검증 상태, 실패한 시도, 정확한 경로는 이 구분을 실행 가능한 형태로 만듭니다. 과거를 버리는 기술이라기보다, 과거를 매번 전부 다시 읽지 않도록 연결하는 기술로 이해할 수 있습니다.

이 논문의 의미는 긴 문맥의 가치를 없애는 데 있지 않습니다. 원문이 명시하듯 긴 문맥이 유익한 작업은 여전히 있을 수 있습니다. 실험이 보여 주는 것은 긴 입력과 긴 행동 이력이라는 두 특성이 **곧바로 큰 활성 문맥의 필요성을 뜻하지는 않는다**는 점입니다. 현재 상태를 잘 남기고 필요한 자료를 다시 읽는 능력을 함께 평가해야 에이전트의 정확도와 비용을 제대로 판단할 수 있습니다.

검토 범위는 arXiv 2611.05306v1의 본문 1–6절, 부록 A–G, Figure 1–8, Table 1–17입니다. 참고문헌에 인용된 연구 전체를 독립 검토하거나 원문 실험을 재실행하지는 않았습니다. 게시용 원문 이미지는 핵심 설명에 필요한 Figure 3의 SAC 상태 갱신·다음 대화 부분만 최소 범위로 인용했습니다. arXiv의 영구 비독점 게시 라이선스를 제3자에게 포괄적인 재사용을 허락한 CC 라이선스로 해석하지 않았습니다.
